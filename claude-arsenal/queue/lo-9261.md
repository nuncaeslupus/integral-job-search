# S12: move free-text capability into the machine-readable step model

## What this is

T28 measures `profile_capture_coverage` over the steps that put candidate free
text in front of a writer. It derives the *step set* live from
`status/spec-v2-steps.json`, and it derives *which steps it actually drives*
from the registered drivers. But the middle question — **does this step take
free text about the candidate at all?** — is not in the model, so T28 carries
one hand-made boolean per step (`ACCEPTS_CANDIDATE_FREE_TEXT`).

T28 names this honestly rather than hiding it, and guards it: a step the JSON
lists that the map has not classified is a measured violation. So this is not a
bug. It is the one part of that gate's denominator a machine does not supply.

## Why move it

- **A new step defaults to unclassified rather than to a declaration.** Today the
  guard catches it *after* it lands and fails the gate; the author then has to go
  and edit a Python constant in another module. Having the step declare its own
  capture expectation puts the decision where the step is defined, at the moment
  it is written.
- **It removes the last unmodelled term.** The whole reason the step set is read
  live is that a checker holding its own copy of the model is correct the day it
  is written and silently wrong on the next addition. This term has the same
  shape and the same failure mode, just smaller.
- **`automatic` is not it.** Only `understanding` is `automatic: true`; the field
  says "no candidate is present", not "no free text about the candidate is
  taken". Ranking is an ordinary conversation that only presents; Identify
  writes nothing for an unidentified session. Reusing `automatic` would be wrong
  and is recorded here so it is not proposed.

## What it costs, and the honest counter-argument

This is a schema migration on `status/spec-v2-steps.json` — the file S1/S2 own,
that `step_specs`, `step_graph`, `step_runtime`, `step_gates` and `process_spec`
all read, and whose shape several gates measure. That is real blast radius for
one boolean.

**And it does not remove the judgement, it relocates it.** Someone still decides,
per step, whether that step takes free text; the gain is that the decision lives
beside the step and a new step cannot silently omit it. Whoever picks this up
should confirm that gain is worth the migration before doing it, and is entitled
to close this as "not worth it" with that reasoning recorded.

Raised by review on PR #27, which recommended keeping T28's approach and doing
this as follow-up.

## Acceptance gate

Every step declares whether it takes candidate free text, and `profile_capture`
reads that declaration instead of its own map.

```bash
uv run --extra dev pytest tests/test_profile_capture.py tests/test_step_specs.py -q
uv run python -m jobsearch.profile_capture --write-evidence
```

```gate
unclassified_free_text_steps == 0
evidence: status/evidence/S12.json
key: unclassified_free_text_steps
```

The metric counts steps in the live model carrying no free-text declaration. It
is deliberately not "the map matches the model" — that is what T28's drift guard
already asserts. It is that **the model itself carries the fact**, so the map can
be deleted.

## Tests

`test_every_step_declares_whether_it_takes_candidate_free_text` — the migration's
own completeness, and the check that stops a step being added without one;
`test_profile_capture_reads_the_declaration_not_a_local_map` — asserted by
changing the declaration and watching coverage follow, since a module that reads
the model but keeps a fallback map has not moved anything;
`test_coverage_is_unchanged_by_the_migration` — the same four surfaces measured
before and after, so a schema change cannot quietly alter what is counted.
