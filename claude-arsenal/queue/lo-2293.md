## What this is

`docs/product-shape.md` proposes: a conversation moves the tool, phases are
skills, checkpoints are scripts with numbers, state is files so it resumes, and
the whole thing is packaged as a Claude Code plugin over this repo.

This task turns that proposal into something mechanical. The gate is not "a
document exists" — it is that **every phase has a named checkpoint script that
returns a number**, so no phase can advance because it felt finished.

## Deliverables

1. A `steps.yaml` (or equivalent) naming each step, its skill, its checkpoint
   metric and threshold — the table in `docs/product-shape.md` as data. Note
   that document numbers the candidate's **steps** independently of the
   specification's delivery **phases**; keep them distinct here too.
2. A checkpoint runner that, for a given step, reports the metric and whether
   the threshold is met. Steps whose implementation does not exist yet report
   `not_implemented` rather than passing.
3. `phase_checkpoints_defined` = 1 only when every step in the table has a
   runnable checkpoint or an explicit `not_implemented` — a step silently
   missing from the runner is the failure this catches, and an empty metric is
   indistinguishable from a forgotten one.

## Decide first

Three questions in `docs/product-shape.md` need the owner's answer, and two of
them change what gets built:

1. One long first interview, or several resumable sittings?
2. Traits scored continuously, or held as episodes until a stated minimum?
3. Multi-user from day one? The spec requires a multi-user profile schema, but
   a plugin installed per machine is effectively single-user — settle it before
   the profile store grows.

## Tests

`test_every_step_has_a_checkpoint` in `tests/test_steps.py` — a step in the
table with no checkpoint entry fails; `test_an_unimplemented_step_does_not_pass`
— `not_implemented` is not a pass.
