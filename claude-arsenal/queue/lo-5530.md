# S11: test mode — a meta channel that does not disturb the session

Owner request, 2026-08-18. **Design is not settled — this payload records the
requirement, the constraints, and the open choices. Agree the shape before
building.**

## What it is for

Once the tool runs end to end, the way to improve the thirteen step skills is to
run a real session and notice, in the moment, where the protocol was wrong: a
question that should have been asked, a follow-up that was missed, a tone that
landed badly. Those observations are worth most while the conversation is live
and worth nothing if writing them down derails the conversation.

So: a second channel, open during a session, carrying notes **about the tool**
while the first channel carries the session **as a candidate would experience
it**.

## The requirement that drives everything

**The session must proceed exactly as a real one.** The moment the tool
acknowledges a note, adjusts its next question, or apologises, the run stops
being a test of the skill and becomes a test of the skill plus a correction. A
note is captured silently and changes nothing until the person says otherwise.

That is also what makes silent capture dangerous: a note that is mis-parsed or
missed is invisible by design. Whatever the mechanism, there must be a way to
**see what has been captured without leaving the session** — a note that
vanished quietly is worse than one that interrupted.

## The owner's proposal, and the problem with it

Proposed: everything in `[...]` is meta. Session continues without mentioning
it; `[... Let's address it now]` opts into acting immediately.

**The collision is the problem, and it is not hypothetical.** This tool's main
input is pasted job adverts and CV text. Adverts are full of brackets —
`[Remote]`, `[Barcelona]`, `[sic]`, bracketed section headers. A candidate
pasting an advert containing brackets would have part of it eaten as meta, and
under silent capture they would not be told. The one surface that must never be
corrupted is the pasted advert: T11 keeps `text` byte-for-byte verbatim because
extraction evidence spans are offsets into it.

A second, smaller problem: the proposal puts two different things in one
channel — an observation ("you should have asked X") and a control instruction
("address it now"). They want different handling and probably different markers.

## Options to decide between

1. **A rarer sigil** — `[[...]]` or `((...))`. Keeps the inline feel, collides
   far less than single brackets. Still collides in principle.
2. **A slash command per note** — `/note <text>`. No collision at all, but
   heavier to type mid-flow, and the command surfaces in the transcript.
3. **Sigil plus a guard**: `[[...]]` inline, *and* meta parsing suspended while
   the turn is a paste (long text, or explicitly `/paste`). Best of both, more
   machinery.
4. **A separate channel entirely** — notes go somewhere that is not the
   conversation. Cleanest semantics, worst ergonomics, and the owner explicitly
   wants to type inline.

**Recommendation to argue about:** (3) — `[[...]]` for a silent note, `[[! ...]]`
for "act on this now", and no meta parsing inside a paste. Separating the
*observation* from the *instruction to act* means the end-of-session pass can
treat every silent note uniformly.

## Constraints that are not negotiable

- **A test note is never candidate evidence.** It is a fact about the tool, not
  about the person. It must not reach `profiles/<handle>/evidence.jsonl` or any
  derived file — the same reasoning that put the decline ledger in `session/`
  rather than the evidence log (T40). A session used for testing must still
  produce a clean profile, or the test corrupts its own subject.
- **Capture the step that was live when the note was made.** Session state (T35)
  and the step runtime (T34) already know it. A note reading "should have asked
  about qualifications" is actionable when attached to step 3; without it,
  somebody has to reconstruct where the conversation was.
- **Notes become queue tasks.** Their whole value is improving the skills, and
  this repository's way of turning a finding into work is a task with a gate.
  Ending a test session should seed them — or at minimum print them in a form
  ready to seed, with the step and skill named.
- **Entering test mode is explicit and visible in the record**, so nobody later
  mistakes a test session's artefacts for a real candidate's.

## Open questions for the owner

- Does test mode apply to a **simulated** candidate (invented answers) as well
  as a real self-run? If simulated, the profile it produces is fiction and must
  be marked as such, or it pollutes the corpus of real profiles.
- Should a note be editable or retractable mid-session?
- End-of-session: seed tasks automatically, or print a reviewable list?

## Acceptance gate

A test-mode session captures every meta note with its live step, changes nothing
in the visible conversation, writes nothing into the candidate's profile, and
ends with the notes recoverable.

```bash
uv run pytest tests/test_test_mode.py -q
uv run python -m jobsearch.test_mode --check
```

```gate
test_notes_reaching_candidate_evidence == 0
evidence: status/evidence/S11.json
key: test_notes_reaching_candidate_evidence
```

## Tests

`test_a_meta_note_never_reaches_the_evidence_log` — the constraint above, and
the one whose failure is invisible;
`test_a_pasted_advert_containing_brackets_is_not_eaten` — driven by a real
corpus ad, since the corpus is the thing at risk;
`test_the_visible_conversation_is_byte_identical_with_and_without_notes` —
what "changes nothing" has to mean to be testable;
`test_a_note_records_the_step_that_was_live`;
`test_notes_survive_to_the_end_of_the_session_and_are_recoverable`.
