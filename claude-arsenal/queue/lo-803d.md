# T50: wire an intake capture driver now that the CV store gives it a surface

## What changed

T28 classifies **intake** as a step that takes candidate free text
(`ACCEPTS_CANDIDATE_FREE_TEXT["intake"] = True`) but has no entry in
`SURFACE_DRIVERS`, so it is reported `pending_implementation` — correctly, at
the time: nothing had been built for it to drive.

S4 has since built it. `jobsearch.cv_store` gives intake a real conversational
free-text path (`add_conversation_entry` / `set_conversation_scalar`) for the
candidate who arrives with no CV and builds the store by talking. That is a
surface that accepts free text about the candidate, which is exactly what T28
measures.

So intake should move from **"not yet built"** to **measured**, and
`profile_capture_coverage` should count it.

## Why this is worth doing rather than leaving

`pending_implementation` exists so that "nothing was built" is never conflated
with "built and drops the input". That distinction is honest, but it is only
honest while it is *true*: a surface that has been built and stays in the
pending bucket is a gap the gate reports as a non-problem. The bucket has to
empty as the surfaces land, or it slowly becomes the place unmeasured work goes
to be forgotten.

Found by the S4 worker and reported rather than fixed, since `profile_capture.py`
was outside its brief.

## What to check while doing it

- **Does intake capture actually reach the evidence log, or only `master.json`?**
  S4's store is its own artefact with its own provenance. If a conversational
  intake answer is *only* stored there, then wiring a driver means deciding
  whether it should also append an evidence row — and whether that duplicates
  what `master.json` already records. Decide deliberately; do not write the row
  twice just to satisfy a counter.
- **Non-insistence and the private default** apply as they do to every other
  driver — reuse `capture()` rather than writing rows directly.
- The driver must **run the real production function**, not a test seam. That is
  the rule that let T28 find the feedback gap in the first place.

## Acceptance gate

`profile_capture_coverage` still reads 1.0 with **intake among the measured
surfaces rather than the pending ones**.

```bash
uv run python -m jobsearch.profile_capture --write-evidence
uv run --extra dev pytest tests/test_profile_capture.py tests/test_cv_store.py -q
```

```gate
profile_capture_coverage == 1.0
evidence: status/evidence/T28.json
key: profile_capture_coverage
```

The gate reuses T28's metric deliberately — this task adds a surface to that
measurement rather than inventing a second one. **The number alone cannot show
this task was done** (it was already 1.0 over four surfaces), so the test below
is what actually pins it.

## Tests

`test_intake_is_a_measured_surface_not_a_pending_one` in
`tests/test_profile_capture.py` — asserts `intake` appears in
`captured_surfaces` and not in `pending_implementation_surfaces`, which is the
only thing that distinguishes this task from a no-op;
`test_a_conversational_intake_answer_reaches_the_evidence_log` — the behaviour,
driven through the real `cv_store` entry point.
