## Technical solution

### Architecture overview

A local Python package with four subsystems, layered so each depends only on the ones below
it. The dimension model sits under everything: it is data, not code, and every layer reads it.

```
                    ┌──────────────────────────────────────┐
   MATCH            │ prefilter → extract → rank → explain │
                    └───────────────┬──────────────────────┘
                                    │ reads offers + profile
        ┌───────────────────────────┼───────────────────────────┐
        │                           │                           │
   ┌────┴─────┐               ┌─────┴──────┐            ┌───────┴────────┐
   │ SUPPLY   │               │  PROFILE   │            │ feedback loop  │
   │ connect  │               │ elicit →   │◄───────────┤ "not this one  │
   │ normalize│               │ evidence → │            │  because…"     │
   │ dedup    │               │ rebuild    │            └────────────────┘
   └────┬─────┘               └─────┬──────┘
        │                           │
        └───────────┬───────────────┘
                    │ both read
          ┌─────────┴──────────┐
 ONTOLOGY │ dimensions/*.yaml  │  ← the spine (data)
          │ corpus/ (labelled) │  ← ground truth + elicitation stimuli
          │ docs/METHODS.md    │  ← every method and formula, link-checked
          └────────────────────┘
```

The corpus serves three consumers — extraction ground truth, ranking ground truth, and
reaction-elicitation stimuli — which is why it is the pacing item and why its disjoint-split
discipline is a gate rather than a convention.

### Data flow

**Onboarding.** `dimensions/` → question bank → candidate free text → extraction → append to
`evidence.jsonl` → `rebuild` → `profile.json` + `stories.jsonl` + `weights.json`. Reaction
elicitation draws stimuli from the corpus's *elicitation* split and appends to the same log.

**Search.** connector → normalised offer → dedup → lexical prefilter → LLM structured
extraction (evidence spans + `unmapped_concepts`) → cached by `offer_id + extractor_version`.

**Ranking.** offers × `profile.json` × `weights.json` → Pareto frontier → salary-equivalent
ordering within the frontier → facet lists → explanations citing verbatim spans.

**Feedback.** candidate reaction → `evidence.jsonl` → `rebuild` → next ranking differs.
Nothing is mutated in place; the profile is always a pure function of the log.

### Technology choices

| Choice | Justification |
|--------|--------------|
| Python 3.12+, `uv`, `ruff`, strict `mypy`, `pytest` | Matches the arsenal `python-bootstrap` toolchain already vendored here, so scaffolding is a solved problem rather than a decision |
| YAML for `dimensions/`, JSONL for logs, JSON for artefacts | Dimensions are hand-edited and want comments (YAML); logs want atomic append and readable diffs (JSONL); artefacts are machine-written (JSON) |
| Files, not a database | Two candidates and a few thousand offers. Git gives history and diffing for free; SQLite is a later migration if volume demands it, and the schemas above are already row-shaped |
| Pydantic for schema validation | Contracts in §5 are the project's backbone; a declarative schema that fails loudly beats hand-rolled checks |
| LLM extraction behind a cheap lexical prefilter | Extraction is the recurring cost. The prefilter's job is recall, not precision — see T14 |
| No web UI in v1 | CLI output is enough to read a ranked list and react to it. A UI would consume the whole slice's budget without testing any hypothesis |

### Out of scope

- Phases 6–8: scheduling, CV/cover-letter generation, outcome tracking, email sensor,
  interview rehearsal, recommendations. Their v1 dependency (the elicitation engine) is in.
- Enrichment from outside the ad beyond writing-style features — no review-site scraping yet.
- More than one live portal connector.
- Any outward action. Nothing submits, sends, or contacts.
