# T82: The application status vocabulary

## Acceptance gate

```gate
applications_with_a_noncanonical_status == 0
evidence: status/evidence/T82.json
key: applications_with_a_noncanonical_status
status-key: gate_status
```

```bash
uv run --extra dev pytest tests/test_lifecycle.py -q
uv run --extra dev python -m integral.lifecycle
```

`src/integral/lifecycle.py` must write `status/evidence/T82.json`. It already writes `status/evidence/S5.json` for another task — add this record beside it rather than replacing it, so both gates keep reading. **A gate must never name a file no module produces** — the file not existing yet is the honest state of an unstarted task; the file existing but empty of this metric is not.

The `bash` block regenerates it; the `gate` block asserts the number in it.

## Why

`applications/{offer_id}/` records what was sent and when, and has no vocabulary for what happened next — so 'what became of this application' is not a thing the tool can state.

Canonical, underscored (`status/spec-v3-silent-success.md` §5.2):

| Status | Class |
|---|---|
| `drafted`, `applied`, `interview`, `offer` | Open |
| `hired`, `rejected`, `no_response`, `offer_declined`, `withdrawn` | Final |

Legacy space-spellings are **accepted on read, never written** — tolerance at the boundary, not a rewrite of stored records.

**Why this is in scope while Phase 7 is deferred:** it is the schema Option C's outcome calibration reads. Dropping it as 'Phase 7, not now' is the one thing in this increment that would foreclose the increment after it.

## What it must not become

A vocabulary's entire value is in being fixed, so do not add a status because a case seems unhandled — raise it instead.

**Never infer `hired` or `offer_declined`.** Accepting or declining is the candidate's decision and is recorded only when they say so. This matters now because it is the rule the deferred mail sensor will inherit.

**A zero-violation count over an empty input set is not a pass.** The gate counts
violations, and nothing counted is also zero — so the evidence record must carry
`applications_with_a_noncanonical_status_evaluated` (application records read) and the gate is only meaningful while that count is
non-zero. This is the failure this whole increment is about, turned on its own gates:
a check that reports success over work it did not do. Assert the denominator.

## A zero count must prove the mechanism ran — 2026-08-26

This gate asserts a **violation count of zero**, and an empty input set produces
zero too. As written it could pass without evaluating a single offer, verdict,
ranked result, document, keyword, application or technique — which is *precisely*
the failure class this increment exists to catch, reproduced inside its own
acceptance criteria.

The gate block therefore carries `status-key: gate_status`, and the producing
module must honour it:

* record **``application_records_checked``** — how many inputs were actually evaluated — in the evidence
  file, beside the violation count;
* write **`gate_status: "unmeasured"`** whenever that count is `0`, and
  `"measured"` otherwise.

`gate_evidence.py` reads `status-key` before it reads the metric and exits **3** on
`unmeasured` — "the check ran, and what it found is that this cannot be scored
yet". Not a pass and not a fail, which is the honest third outcome for a run that
processed nothing. That is the same mechanism `lo-6f53` uses for
`extraction_macro_f1`, so this is existing machinery rather than a new rule.

**A second assertion in the gate block would not have worked**: line 1 of a `gate`
fence *is* the gate, one metric per block. Making the emptiness visible through the
status key is what makes the invariant executable rather than prose.
