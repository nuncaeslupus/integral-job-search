Owner note (2026-09-22, step `sourcing`): on Greenhouse and on talent.com an
advert is often titled only "Software Engineer", and the vocabulary that decides
whether it is worth reading — "agentic AI engineer", "prompt engineer",
"automation engineer", "AI engineer", "Claude Code" — appears only in the body.
A query narrow enough to name that vocabulary therefore never sees the advert
that contains it. The proposal is to query the umbrella term, fetch the bodies,
and let a regex over the body say which ones to read first.

Measured live on talent.com before filing this, with every body fetched:

| query | rows | bodies carrying the aim vocabulary |
|---|---|---|
| `software engineer` (broad) | 16 | 4 |
| `ai engineer` (narrow) | 13 | — |

Three of the four were titled "Senior Software Engineer", "Senior Software
Engineer" and "Staff Software Engineer", and **none of those three appears in
the narrow query's 13 rows**. The fourth was titled "AI Software Engineer",
which the narrow query does find. So the broad query is what recovers them.

The caveat is part of the note rather than a footnote to it: **n=16, one query,
one board, one day**, and the board reordered its rows between two runs minutes
apart, so the two samples are not the same adverts. That is enough to justify
building the mechanism; it is not enough to state a recall figure, and this task
must not commit one.

## What the mechanism has to be

**A mark, not a filter.** `bulk_filter.reduce` already holds the rule that only a
hard fact stated in the advert may delete, and an advert that never writes the
word is not an advert that fails the criterion. A body regex that *dropped* the
non-matching rows would delete on an absence, which is the fail-open direction
this repo keeps catching — it would read as precision while silently costing
recall nobody could see. The mark is a reason to read first, and the unmarked
offers stay in the list.

**There is nowhere to put it today, which is most of the work.** `matches_aim`
runs in `_one_board`'s row loop, *before* the detail fetch, and only on boards
that cannot be steered:

```python
if not steerable and not matches_aim(item, phrases):
```

A steerable board — talent.com is one — therefore has no body-level narrowing at
all: every queried row is written as an offer. So this needs a new step after
`_detail_record` lands the body, not a change to `matches_aim`.

**It is bounded by ceilings it will reach.** A broad phrase spends one of
`PHRASE_CEILING = 6`, every row costs a fetch against `DETAIL_FETCH_CEILING = 40`,
and the offers land against `OFFER_CEILING = 50`. On the measured run a broad
query spent 16 fetches to recover 3 adverts. Whatever this task builds has to
say what happens when the broad query alone exhausts the detail budget, rather
than discovering it in a live session.

`page_count` is hardcoded to 1 in `source()`, so recall is capped at page one
whatever this task does. That is not this task's to fix — note it, do not widen
scope into it.

Adjacent but not the same task: `t-0b0a29ea` (T187) expands a *narrow* term into
synonyms for the web-search fallback. This one widens to an umbrella term and
narrows on the body, on connector boards. Neither subsumes the other.
