Imported from issue #315

`connectors/getmanfred_es/connector.yaml` maps `location_remote: remotePercentage` and maps nothing to `location_raw`, so a Manfred offer's physical location never reaches a parsed offer. The list API carries it:

```
"locations":["Marbella, España"]
"locations":["Madrid, España"]
"locations":[]
```

Found by CodeRabbit on #264. It matters more than "Minor" suggests: the candidate this tool is built for is constrained to Barcelona with `relocation.willingness: "no"`, so city is the field that decides whether an offer is reachable at all. `location_remote` does capture remote-ness, so what is lost is specifically the physical city on non-remote and partly-remote roles.

**It cannot be mapped today, and that is the actual issue.** `location_raw: locations` maps nothing, because two things refuse it in `src/integral/connectors.py`:

- `JSON_PATH = re.compile(r"^[A-Za-z_@][\w@-]*(?:\.[A-Za-z_@][\w@-]*)*$")` — every segment must begin with a letter, `_` or `@`, so `locations.0` is not a compilable path.
- `dig` walks dicts only (`if not isinstance(node, dict) or key not in node: return None`) and treats landing on a container as a miss — deliberately, and the docstring explains why: `str({...})` would hand `build_offer` a Python repr as though the board had published it, and for a salary key that is the difference between "no figure" and `Salary(stated=True)` carrying `"{'@type': ...}"`.

So the fix is not a line in one connector's YAML. It is **array indexing in the shared JSON path resolver**, which all fifteen connector packages route through.

**Why this is filed rather than folded into #264.** CLAUDE.md: *"for any task whose gate can pass while the code is wrong — parsers, matchers, normalisers, anything comparing two encodings of the same thing — a session other than the implementer writes adversarial fixtures."* Extending a path grammar and a resolver is squarely that, and T70 is the precedent: ten defects over five review rounds, eight of them introduced by the session fixing the previous one, every round green.

Nothing is currently *wrong* — a field is absent, and "absent beats invented" is already this connector's stated principle, recorded in its own `salary_period` comment. A wrong location would be worse than a missing one.

**What the work is**

1. Decide the grammar. `locations.0` (numeric segment) is the obvious spelling; `locations[0]` needs bracket syntax the regex has no room for. Either way the decision is which spellings are *refused* — the resolver's whole safety property is that it consumes the string against a regex and never evaluates it.
2. `dig` indexes a list when the segment is numeric, and still treats landing on a container as a miss.
3. Map `location_raw: locations.0` in `getmanfred_es`, with coverage that `"Marbella, España"` survives into a parsed offer **and** that `"locations":[]` yields no `location_raw` rather than an empty string or an exception.

**Adversarial cases the second reader should derive from the grammar, not from the code** — negative index, index past the end, index into an object, a key that is literally `"0"` in a dict (does `locations.0` mean element 0 or key `"0"`? — the answer must be stated, not discovered), a nested `a.0.b`, an empty array, an array of objects where the element is a container and must therefore miss, and a segment like `01`.
