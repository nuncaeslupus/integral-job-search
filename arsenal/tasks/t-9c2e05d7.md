## Where this comes from

`step-11-application` writes `carta.md` and `cv.md`, and stops. What an employer
receives is a PDF or nothing — nobody emails a recruiter a Markdown file. On the
DOMMA application both HTML documents were hand-built inside the session, twice
(once, then again when the palette changed), and the second build had to
re-derive the same decisions from scratch because none of them lived anywhere.

The decisions that have to survive, all of them met by hand there:

- **One file.** Inline `<style>`, image as a `data:` URI. An employer's mail
  client and a browser's *Print → Save as PDF* both handle it; a folder of
  assets does not survive either.
- `@media print { @page { size: A4; margin: 22mm 24mm } }`.
- `orphans: 3; widows: 3` and `break-after: avoid` on headings — without them a
  two-page letter breaks after a heading and orphans a line, which is what a
  first draft of the DOMMA letter did.
- Markdown is the source; the HTML is generated. Editing the HTML by hand is how
  the two drift.

**Escaping order is the one non-obvious bug**: `html.escape()` **first**, then
the `**bold**` substitution. Reversed, the apostrophes in Catalan contractions
came out as `&amp;#x27;` — met and fixed in that session.

## What to build

`integral.application_render` — Markdown in, single-file HTML out, for both the
letter and the CV, with the CV's photo header as a variant rather than a second
template. No Markdown library dependency: the subset in use is headings, bold,
paragraphs and bullets.

## Tests

`test_escape_precedes_bold_substitution` — an apostrophe inside a bold span
survives as `'`, not `&amp;#x27;`.

`test_output_is_a_single_file` — no external `src`, `href` or `@import` in the
rendered document.

`test_print_rules_are_present` — `@page` size A4, and orphan/widow control.
