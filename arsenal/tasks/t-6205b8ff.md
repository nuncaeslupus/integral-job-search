Imported from issue #308

Found by CodeRabbit on #304, which flagged that T101's row was unticked while T103 depends on it and is complete.

The pair really was contradictory, but the drift was not T103's. **47 of 123 archived-merged tasks still carried an unticked `☐` row** in `status/plan.md`. Ticked on `main` in `e32a541`; this is the check so it cannot recur.

## Why it happens

Nothing ties the tick to the archive. `open_task_pr.sh` moves the task file into `arsenal/tasks/_history/` with `status: merged` in the same diff, and `integral.plan_v2` checks the label, the gate form and plan/queue agreement — but no one checks the box. The two records simply drift apart, silently, one merge at a time.

## Why it matters more than bookkeeping

`status/plan.md` is what a session reads to see where the project is. A board that reports 44% of its finished work as unfinished is not a status document, it is noise — and the failure is the one this repository keeps legislating against: a record that quietly stops describing what it claims to describe, while every gate stays green.

## Scope

Extend `integral.plan_v2`: every task with a file in `arsenal/tasks/_history/` carrying `status: merged` must have a ticked row, and the converse — a ticked row whose task is still live in `arsenal/tasks/` is the same fault the other way round. Report it as a counted metric with a denominator, not a boolean.

`plan_v2` already resolves labels to task files for `plan_queue_task_drift`, so the join exists; this is a second assertion over the same pairing.

Do this **after** `e32a541`, or the check lands red on 47 rows.

## Gate

`merged_tasks_with_an_unticked_plan_row == 0`, denominated by the number of terminal tasks compared, with a floor so a scan that finds no archive reports `unmeasured` rather than a clean zero.
