Imported from issue #553

`_numbers_in` (`src/integral/connectors.py:1195`) resolves every number in a cell
"without guessing", and `range_low`/`range_high` then require **exactly two**. A band
whose thousands are grouped with a **space** defeats that:

```
"33 000 – 45 000 PLN / month"  ->  _numbers_in -> [33.0, 0.0, 45.0, 0.0]
```

Four numbers, so both takes decline and the whole band is lost. The refusal is
fail-safe — nothing wrong is stored — and the row is genuinely unread.

Found while landing T200 (#549), and **declared** there rather than fixed:
`connectors/nofluffjobs_en/fixture/salary.json` row `1` carries
`verdict: "refused"` with that reasoning, so T200's
`boards_that_publish_a_salary_we_do_not_read == 0` counts it as a written-down
refusal and not as a board we silently fail to read. PLN is not the obstacle — it is
in `_CURRENCIES` and `take: currency` resolves it on that very row.

## Why it is its own task

Space-grouped thousands are a **number-parsing** change, not a connector change: every
connector in the library shares `_numbers_in`, and the four conventions collide.
`33 000` is thirty-three thousand in fr/pl/sv/cs (and in SI, which prescribes the thin
space); `33 000` inside `1 2 3 4` is four numbers; and a narrow/thin/non-breaking space
(U+00A0, U+202F, U+2009) is what the boards that use it actually emit, not U+0020. A
rule that merges `<digits><space><exactly three digits>` has to not merge a headcount
beside a year, or an hourly rate beside an annual band — the same "exactly two" hole the
existing comment at `:1223` was written about.

So it needs adversarial fixtures from a **second session** (CLAUDE.md, *"Fixtures for a
correctness-critical gate are written by a second session"*) — this is squarely a
normaliser comparing two encodings of the same thing.

## Acceptance gate

```bash
uv run python -m integral.connector_salary_audit
```

`boards_that_publish_a_salary_we_do_not_read == 0` with
`salary_rows_refused` **strictly lower than 7** and
`salary_expectation_mismatches == 0` — i.e. the nofluffjobs row moves from `refused`
to `read` with `min: 33000`, `max: 45000`, `currency: "PLN"` in its committed fixture,
and no row that reads correctly today starts reading differently. The second number is
the one that matters: a permissive merge rule buys the PLN row by mis-reading somewhere
else, and only the mismatch count sees that.
