Candidate note (Ivan, 2026-09-16, step `sourcing`): a genuine conversational turn
>=400 chars containing two URLs and no `/paste` prefix was classified as a paste by
`detect_guard()`'s length heuristic (`PASTE_CHARS`), so its `[[...]]` meta note was
silently declined (`unparsed_markers`) instead of captured. Reproduced by replaying
the turn through `MetaChannel.feed()` with the guard forced off (`guard="none"`),
which recovered the note.

This is a plausible root cause for the "old comments feel lost" pattern the ledger
otherwise cannot explain by itself — all 51 historically captured notes across 5
sessions show `captured == shown`, so the ledger never lost anything that got parsed
in the first place. The loss happens one step earlier, at classification.

Fix direction: the guard needs to tell a long typed answer from a pasted advert by
more than character count alone (e.g. bracket/advert-shaped structure rather than
raw length), so an ordinary prose turn that happens to contain URLs doesn't trip it.
Whatever the heuristic becomes, every declined marker must stay visible in the
end-of-session review exactly as it is today (`unparsed_markers`).
