From a test-mode note captured 2026-09-06 at step `identify`:

> We have a problem here. How to differentiate between a real live user session and a coding session for the repo?

Today nothing answers it. Three facts exist and none of them are joined: a resolved handle in `session/state.json`, a test-mode ledger under `<profiles root>/.test-mode/`, and the `fiction: true` mark a simulated profile carries. A session working on the repository has none of the three, and so is indistinguishable from a candidate session that has not identified anyone yet — which is exactly the state step 0 is *supposed* to be in.

The cost is not theoretical. This session was both at once: it ran the thirteen-step process for a real candidate and merged six pull requests, and the only thing keeping the two apart was the operator's own judgement plus `[[...]]` markers. S3's hook refuses a `profiles/` write outside the *identified handle*; it has nothing to say about a session that identified nobody because it was writing Python.

What is wanted is one function that answers it — `session_kind()` — and one place that records the answer, so an engineering session cannot write into a candidate's tree by accident and a candidate session is never filed as a test.

**Measured by running, not by reading.** The precedent is T121 and T136: a checker that greps for the right shape is defeated by comments and by unused strings. So the gate builds named cases — a tree with a resolved handle and no ledger, a tree with a ledger and `fiction: true`, a bare repository checkout, a session that identified nobody and wrote no profile — and counts the ones `session_kind()` gets wrong. Weight fail-open: calling an engineering session a candidate session is the answer that lets a write through.
