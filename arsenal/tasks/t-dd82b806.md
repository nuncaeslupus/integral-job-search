Found by the second-reader audit of #295 (T89). This one is genuinely nasty because every check in the path is satisfied.

`yaml.safe_load` is YAML 1.1. Measured on this repo's pyyaml:

- `01234` → `668` (octal)
- `12:30:00` → `45000` (sexagesimal)
- `0x1F` → `31`
- `yes` / `on` / `NO` → booleans

A `body_json` value like a leading-zero reference number, a time-of-day filter, or a `Remote: no` flag **silently becomes a different value on the wire**. Nothing refuses it: these are all valid JSON types, so neither the literal-body walk nor the `serialise_body` backstop sees anything wrong. The connector author's file says one thing and the request says another, and the gate is green.

## Options

1. Refuse an **unquoted** scalar that resolves to a different value than its source text. Needs a loader hook that keeps the raw scalar alongside the resolved value. This is real protection.
2. Document the trap prominently and require quoting in the connector-authoring guide. Cheaper, and at least honest.

Prefer 1. The whole point of `body_json` being "a literal body" is that what is written is what is sent, and today that is false for four scalar shapes.
