## The claim that is false

`address_key_sites_outside_every_block` records `[offset, key]` per site, and round 8's
argument for that shape was: *a lost block adds an entry, a vanished key removes one, and
they cannot share a byte offset.* Offsets are unique **within** a capture; they are not
**stable across an edit**. An edit that shifts the remaining bytes makes the added and the
removed entry coincide.

## Reproduction

```
before  {"a":{"ip":…,"n":{"y":1}},"b":{"ip":…,"city":…}}
after   {"b":{"ip":…,"city":…,"m":{"y":1}}}
```

`measure()` returns the identical record `[[7, "ip"]]` with `violations == []`, while
`requester_location_blocks` goes `[(36, 76)] → []` and the unscrubbed form leaks
`Barcelona`. Offset 7 either way — no byte counting needed to see it.

`tools/excerpt_fixture.py` is cited in that very diff and is exactly the edit class that
shifts offsets.

## Shape

The family this repo keeps finding: **a check pinned against a proxy for the property.**
A byte offset is a proxy for identity, and it is not invariant under the edits the record
exists to survive. The closed-rule direction is an identity that does not move when
earlier bytes do — a content digest of the site's enclosing object, or the census keyed by
something the edit cannot renumber. Do not answer it with one more constructed case.
