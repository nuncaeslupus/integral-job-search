## The defect

Reported by the owner on 2026-09-10: in a candidate session InfoJobs — the only
general-market Spanish board connected, and the one a pharmacy candidate in
Barcelona needs — returned nothing.

Measured the same day with `integral.robots.USER_AGENT`: every
`/ofertas-trabajo/*` and advert GET answers **HTTP 200, 29,762 bytes**,
`server: bon`, `x-cache: LambdaGeneratedResponse from cloudfront` — a
CloudFront-edge page reading "No podemos identificar tu navegador", canonical
`/distil/distil/captcha.xhtml`. `robots.txt` and `/` still reach origin
(`server: Apache`). `Accept-Encoding: identity`, `Accept`/`Accept-Language`
headers and a ~70 s pause change nothing. On 2026-08-30 the same surface got the
real 1.29 MB listing.

The owner's own Chrome, same network, got the same page and then passed it
**silently** in ~10 s — no CAPTCHA, no click — and rendered the listing: 376
IT offers and 10,755 all-sector offers in Barcelona. So the edge runs a
JavaScript check a real browser passes and a plain HTTP client cannot. It is
not the IP and not the job category.

**Out of bounds, whatever the cost:** replaying the browser's token (`reese84`)
from a plain client, running the check in a headless engine, a browser user
agent on the plain client, a solver, rotating addresses. Each is bot-detection
evasion. Discussed with the owner and ruled out.

## The route

The candidate's own browser makes the request and the engine reads what it
rendered. Nothing crosses from the browser to another client.

* **`list.client: browser`** — a connector names the client its listing is
  served to, as `htmx` already does. Not `auth: candidate_session`: that means a
  signed-in session, InfoJobs needs none, and `meta.yaml` keeps
  `authentication: none` truthfully.
* **Sourcing never sends a `browser` board to the plain fetch.** With no browser
  capture supplied the board is reported *skipped, needs the candidate's
  browser*; with one it is answered from the capture and the fetch log records
  `via: candidate_browser`.
* **A capture names the URL it was taken from**, and answers only that URL, so a
  capture of one search cannot stand in for another.
* The page saves itself into the candidate's Downloads folder (measured: no
  prompt, 1.27 MB, and the **unchanged** connector parsed 5 real pharmacy offers
  from it), so the bytes never pass through the session's context.

Also in scope, because the route is useless without it: the connector was fixed
to IT jobs in Barcelona. `/ofertas-trabajo/{query}/barcelona` keeps the scope
("17 ofertas de auxiliar de farmacia en Barcelona", with the engine's own
`quote(query, safe="")` encoding), where `?keyword=` silently drops it to "todas
las ubicaciones" exactly as `?page=2` does.

And the refusal check it exposed: the engine did report the challenge as
REFUSED, but only because `captcha` sits in the page's **markup**. No
`BLOCK_PAGE_MARKERS` phrase is in its visible text, so renaming one element id
would turn a refused board into an empty one. The real page joins the refusal
samples, with its visible-text markers.

## What the metric counts

`browser_boards_fetched_over_plain_http`: requests for a `client: browser`
board's listing or adverts that reached the plain fetch, across constructed
runs with and without a browser capture. `unmeasured`, not a clean zero, unless
the same runs also collected offers from the capture **and** a plain board still
reached the plain fetch — a sourcing pass that fetched nothing at all would
otherwise score zero.
