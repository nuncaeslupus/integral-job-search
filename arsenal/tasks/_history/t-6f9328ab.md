Found while opening PR #89 (2026-08-20).

`CLAUDE.md` says all five must pass before a merge:

    make lint  test  evidence  verify-subtree  verify-gates

Nothing runs them. Three separate holes, and PR #89 fell through all three:

1. **CI cannot.** GitHub Actions has been out of runner minutes since 2026-08-19 —
   every job on every run fails in 3-5s with `runner_id: 0`, `main` included. So
   `ci.yml` is not an enforcement point today, and `arsenal-queue.yml` is not either,
   which also means the `task-file-landed` hook that opens issue handles never fires.
2. **`open_task_pr.sh` runs the wrong gate.** A worker re-runs `gate_run.sh` on its own
   payload. Nothing in that path runs the repo suite, so a worker can open a green task
   PR that breaks `make test`.
3. **`keyword-guard` only fires on `arsenal/**` branches.** PR #89 was on
   `s12-test-session-findings`, so no check ran on it at all. (Correct by
   design — a PR that is not a task PR should not need `Closes #<issue>` — so
   this is ruled out rather than fixed.)

## The split: which half is ours

**Upstream — `claude-arsenal#175`.** `agents/worker.md` step 4 asks a worker to
"run the host lint gate if one exists", and no script enforces it:
`open_task_pr.sh` re-runs `gate_run.sh` (so the *payload* gate is a real
precondition) but never asks whether the *repo* gate passed. That is the same
"an instruction with no data path behind it is a step that does not happen"
failure `AGENTS.md` records for the closing keyword — the keyword got a data
path, the host gate did not. Editing `claude-arsenal/bin/open_task_pr.sh` here
would be overwritten by the next subtree upgrade and would fail
`make verify-subtree` in the meantime, so it is filed upstream, not patched.

**Ours.** A `make gate` target that runs all five, so the host has one command
for upstream's `host-gate` key to point at, and so a session has one thing to
run instead of five to remember.

The five ran only because a human asked. `make test` then failed on nine title-label
violations that would otherwise have merged.

The fix is an enforcement point that does not depend on runner minutes: a pre-push or
pre-merge hook in the repo, or a `make gate` target that `open_task_pr.sh` calls before it
pushes, with the run recorded so a merge can be refused when it is absent. Prose in
`CLAUDE.md` is not one.

Addressed in: `Makefile` (ours). The bundle half is `claude-arsenal#175` — not patched here.


## What was built

**`make host-gate` — the five, one command.** The aggregate already existed as `ci`, but under a
name that says "what CI runs", and CI is precisely the thing that cannot run here. `host-gate` is the
name `claude-arsenal` points a worker at, so the hook has something real to call the day it lands.
`ci` now depends on it rather than repeating the list: two lists of the same five drift, and the one
that drifts is the one nobody runs.

`gate` was already taken — it records T1's lint exit code, one check — and reusing it would have made
"the payload gate ran" indistinguishable from "the repo gate ran", which is the confusion this task is
about. `payload_gate_is_not_the_repo_gate` records that they are still distinct.

**`CLAUDE.md` leads with it**, and says plainly that `make gate` is a different thing.

## What measures it

`required_gates_with_no_enforcement_point` reads the `make` targets `CLAUDE.md` requires before a
merge and asks two things of each: is it a real target, and does `make host-gate` reach it. The second
is the one that rots — somebody adds a sixth line to the docs and the target nobody wired up is the
target nobody runs. Reachability is transitive so that `ci: host-gate` counts, rather than the check
pushing the repo back to the duplication it just removed.

The reading lives in `src/integral/repo_gate.py`. Confirmed to fail against the state D-22 was filed
in: with no `host-gate` target the measurement records `-1` (there is no one command to check the list
against), and a required gate the aggregate has forgotten counts 1. Both were reproduced before the
tests were trusted.

## One existing test changed

`test_ci_runs_the_subtree_check` asserted `verify-subtree` appeared on the `ci:` line. Its invariant —
"a check nothing invokes protects nothing" — still holds through `ci` → `host-gate` → `verify-subtree`,
but a substring check cannot see one level of indirection. It now asserts reachability, which is the
same guarantee computed correctly rather than a weaker one.

## Left for someone else

**The worker half is upstream's, and still open.** `open_task_pr.sh` re-runs `gate_run.sh` on the
payload and never asks whether the repo gate passed, so a worker can still open a green task PR that
breaks `make test` — `claude-arsenal#175`. Patching the vendored script here would be reverted by the
next subtree upgrade and would fail `make verify-subtree` meanwhile. The host now holds up its end;
the hook is upstream's to add.

**Nothing yet forces a human to run it.** `make host-gate` is one command instead of five to remember,
and the measurement keeps the list honest — but a pre-push hook, or upstream's `host-gate` call, is
what would make skipping it impossible. That is the remaining half of "an enforcement point that does
not depend on runner minutes".

## Acceptance gate

```gate
required_gates_with_no_enforcement_point == 0
evidence: status/evidence/D-22.json
key: required_gates_with_no_enforcement_point
```

```bash
uv run python -m integral.repo_gate --write-evidence status/evidence/D-22.json
uv run --extra dev pytest tests/test_plan_v2.py tests/test_arsenal_subtree.py -q
```

The `bash` block regenerates the measurement and runs the behavioural half; the `gate` block asserts
the number in the file. Neither alone is the gate: without the first a stale evidence file passes
unchallenged, and without the second a command that exits 0 counts as a gate whether or not it checked
anything.
