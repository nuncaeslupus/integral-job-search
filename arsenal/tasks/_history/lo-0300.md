The two blocks do different jobs and both are required. The `bash` block
regenerates `status/evidence/T42.json`; the `gate` block asserts the number in
it.

## What this is

An extraction that records `salary: 48000` leaves ranking to work out what
that means. An annotation recording *that it sits inside this candidate's
expected band*, that the private insurance they asked for is present, that the
required Catalan is held, turns ranking into comparison rather than computation.

So: a second pass over the extraction, **on this machine**, writing
`annotations/<offer_id>.json` — derived, recomputed whenever constraints or
weights change, and never a field inside the extraction.

## The rule that matters

**The separation matters more than the convenience.** The model sees the
advert and nothing else; the profile is never sent one advert at a time. That is
what keeps `extractions/<offer_id>.json` candidate-independent — cacheable,
shareable, leaking nothing — and it is the single privacy failure that cannot be
undone once it happens.

The gate must be measured over the **actual outbound payload**, not over intent:
a test that asserts the code does not intend to send the profile proves nothing.

## Tests

Write these RED before any production code:

`test_no_profile_bytes_appear_in_an_extraction_payload` in
`tests/test_annotation.py` — a fixture profile with distinctive strings appears
nowhere in any captured outbound request;
`test_annotation_is_recomputed_when_constraints_change`;
`test_extraction_schema_stays_candidate_independent` — an annotation field added
to the extraction schema fails validation.

## How the gate is measured

`integral.annotation.measure` plants two unmistakable strings in a fixture
candidate's free-text constraint fields, serialises what `model_request` would
actually put on the wire for **12 real corpus adverts** (~28 kB), and counts
every planted string that appears in those bytes. The annotation pass runs for
each of those offers while the scan happens, so the number is measured with the
pass working rather than over a pipeline that never annotated anything.

`stated_strings` walks the constraints dump rather than naming fields, so a
constraint field added later is scanned for without anyone remembering; the
schema's own vocabulary (`stated`, `professional`, `remote`) is read out of the
JSON schema and excluded, because those are the model's words and not the
candidate's.
