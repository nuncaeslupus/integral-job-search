## What this is

`vendor/claude-arsenal` is gone. `/init` writes what this repo needs — the
skills, the `claude-arsenal/` runtime tree, and the skill-edit gate in
`.claude/settings.json` — so there is no subtree to pull and nothing to
reconcile.

## Why the subtree went

The v0.36.1 → v1.0.0 pull conflicted on seven files, and the Makefile already
documented why: a squash merge drops the `git-subtree-split:` trailer, so the
next pull replays from a stale base and conflicts on files that carry **no local
edits by construction**. The standing resolution was "take upstream's tree
verbatim" — a ceremony performed every upgrade to reconcile a copy nobody edits.

## Why the skills stayed vendored — the correction

This task first went the other way: it removed `.claude/skills/` in favour of the
plugin declaration v1.0.0 shipped. **That was wrong, and upstream refuted it with
evidence rather than argument** (`claude-arsenal#200`, v2.0.0). A cloud session —
Claude Code on the web, `claude --cloud`, the apps, routines — runs on a fresh
clone on another machine, never reads `~/.claude/`, and **does not install
plugins the repository asks for**. Tested live: with a correct declaration
committed, the marketplace public and the pinned tag returning 200 from inside
the sandbox, `known_marketplaces.json` was absent and `installed_plugins.json`
empty. What a cloud session loads is what was committed.

The declaration is removed rather than kept beside the vendored copies: together
they make every skill live twice — `specify` and `core:specify` both answering —
at twice the listing budget.

So the two counts this task gates are opposites, and confusing them is the whole
risk: **`upstream_subtree_files` must be 0** and **`vendored_skills` must not
be**. `integral.arsenal_source` reports both, because "we removed the tree" and
"we removed the skills" would otherwise be the same clean zero. The skills are
identified by the `.arsenal-vendored` marker `/init` stamps, so a skill this repo
authored sits beside them without being counted as upstream's.

## What changed

- `vendor/claude-arsenal` deleted, with `make verify-subtree`, `arsenal-remote`,
  `arsenal-upgrade`, `update-skills`, `assemble-bundle`,
  `tools/verify_arsenal_subtree.py` and `tests/test_arsenal_subtree.py`.
- **`host-gate` drops to four targets**, so `CLAUDE.md`'s block and
  `tests/test_plan_v2.py` move with it. D-22's `integral.repo_gate` checks those
  two agree, which is what makes it safe to change; its own regex no longer pins
  the count word.
- `/init` at v2.0.0 wires the skill-edit gate into `.claude/settings.json`.
  Plugin hooks do not travel with vendored skills, so vendored skill authoring
  had been ungated here for as long as vendoring has existed.
- `listing-budget` 13,000 → 11,000: v2.0.0 trimmed seven oversized descriptions
  and dropped `lsp-setup` and the old `skill-creator`, so the library measures
  9,231 over 31 skills. 1,769 spare — the same headroom discipline S10 chose
  originally, not the tightest legal number.

## A blocker fixed upstream on the way

v1.0.0 shipped `plugins/core` with `"author": "nuncaeslupus"` where the loader
wants an object, so `core` would not register and this machine sat on 0.1.0 from
months earlier. Fixed in `claude-arsenal#198` → v1.0.1, together with
`make validate-manifests`: `sync_version.py` rewrites the `version` token in
those manifests and never reads the rest, so a manifest the loader rejects could
be tagged and released — and was.
