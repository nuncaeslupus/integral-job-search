Found during the test session of 2026-08-20.

The candidate said: "I can move, but in the province of Barcelona, or maximum to Girona or Tarragona.
I want to sleep home each day." None of T24's ten pinned fields can hold that:

- `location` takes a country and an onsite flag;
- `reach` takes modes (`commute`), not a distance or a region;
- `relocation` refuses `destinations` when `willingness` is `no` — correctly, since he is not relocating.

So the single most filtering thing he said survives only as quote text on an evidence row, and nothing
downstream can filter on it. `filter_hard_constraints` cannot honour a commute radius it has no field
for.

Addressed in: `src/integral/candidate.py`, `src/integral/constraints_step.py`, `step-02-constraints`.

## What was built

**`Location.commutable_regions`, not an eleventh field.** `Location` already owns "where the candidate
is, and the on-site work they'll do without moving", and `accepts_onsite_in_country` was that question
asked too coarsely — one bool over a whole country. The regions narrow it. The pinned set stays at ten,
which matters: growing a field per sentence is how a pinned contract stops being one.

A radius alongside `accepts_onsite_in_country: false` is refused at construction. The pair is
contradictory, the filter reads the bool first and would never reach the regions, and a contradiction
sitting in `constraints.json` looks answered.

**The filter honours it.** `_violates_location` removes an on-site offer whose region is outside the
stated set, with the reason naming both the place and the radius. Two boundaries held deliberately: a
radius narrows *on-site* work and never vetoes a remote role, and an advert that does not say where
the work is cannot be shown to violate it — an ad-side unknown never vetoes, exactly as
`payroll_countries` does not.

**The question gets asked.** `step-02-constraints` now asks how far, when commuting is in scope, and
says to record the places rather than the feeling. A field nobody asks about is never filled.

## What measures it

`unfilterable_stated_constraints` is the general form, not this one sentence: for each of the ten
pinned fields, a real sentence a candidate might say is stated, and the filter must both remove an
offer that breaks it *and* keep one that does not. Requiring both directions is the point — a field
that removed everything would pass a one-sided check while making the stated limit useless the other
way.

The second failure mode is the one worth having: a field that accepts the value and changes no offer's
fate. It looks answered from every angle — populated, asked, coverage passing — and the candidate sees
the same list either way. That is `AGENTS.md`'s inert gate wearing a constraint's clothes.

The reading lives in `src/integral/stated_constraints.py`. It was confirmed to fail against the state
D-20 was filed in: `test_a_constraint_that_filters_nothing_is_counted` rebuilds the pre-D-20 `Location`
and asserts the Sevilla offer survives, so a zero means the check would notice the defect returning.

## A note for whoever reads the plan

The plan row names `tests/test_candidate.py`. No such file exists — T24's tests, and every existing
`filter_hard_constraints` test, live in `tests/test_candidate_attributes.py`, so both named tests went
there. The test *names* are as the plan asked.

## Left for someone else

`commutable_regions` holds named subdivisions, not a distance. "Within 50km" still has nowhere to go,
and turning a radius in kilometres into a region set needs a gazetteer this repo does not have. That is
a real gap, not an oversight — it is recorded here rather than papered over with a number nothing can
compare.

anything.
