## Acceptance gate

```gate
unrecordable_task_gates == 0
evidence: status/evidence/D12.json
key: unrecordable_task_gates
```

```bash
uv run --extra dev pytest tests/test_task_gate.py -q
uv run --extra dev python -m integral.task_gate
```

The `bash` block regenerates `status/evidence/D12.json`; the `gate` block
asserts the number in it. `unrecordable_task_gates` counts the task gates whose
evidence file holds a non-numeric value at the gate's key and whose gate block
declares no `status-key` — measured, and with nowhere to record what the
measurement found.

## What the spec requires

D-2 (`lo-77a6`) binds T15 to three outcomes, not two: a score, a failure, or
**unmeasured** — "an unmeasurable gate must not resolve to a pass or to a
fail". T15's payload repeats it, and `integral.extraction` implements it: with
14 evaluation labels against a floor of 10 per dimension, `measure()` records

```json
{"extraction_macro_f1": null, "extraction_status": "unmeasured", ...}
```

which is the correct and only honest output.

## What the code does

The gate layer has no third outcome. `claude-arsenal/scripts/gate_evidence.py`
exits 0 (pass), 1 (assertion failed) or 2 (declared but missing file, key not
found, **or non-numeric value**). A null lands in that last branch:

```
$ bash claude-arsenal/bin/gate_run.sh lo-25b1
gate_evidence: evidence value at 'extraction_macro_f1' is not numeric: None
gate_run: evidence gate failed for lo-25b1
```

So the one output D-2 requires is the one output the gate reads as a hard
failure. T15 therefore **cannot reach `done` or `merged`** until the corpus
grows past the floor — which needs T25 (`lo-1af2`, `[LAPTOP]`, egress) and
T26 (`lo-9e41`).

## Why this blocks more than T15

T15 gates **fifteen of the twenty-six live tasks** — T42, T43, T45, T17, T18,
T16, and through them S6, T46, T47, T22, T44, T19, T21, T20. This is precisely
the shape T14 was in before #81 folded it: a task held open by a gate nobody
can measure, with the queue behind it. Fixing it there and leaving it here
would be treating the instance and not the disease.

## The two resolutions, and what each costs

**A — split the acceptance.** T15's gate becomes a property of the extractor
that is measurable today (`prefilter_suppressed_positives == 0` is already
computed and holds over 36 positives), and `extraction_macro_f1 >= 0.75`
becomes its own task, blocked on T25/T26, where it belongs — a scoring gate
whose prerequisite is labels. Cost: two tasks where the plan has one, and the
plan row must move with it. Benefit: T15 closes on what T15 actually built, and
fifteen tasks unblock.

**B — give the gate layer a third outcome.** `gate_evidence` learns that an
evidence file may record a metric as explicitly unmeasured — a null beside a
status field — and exits 3 ("could not run"), which `gate_run.sh` already
treats as distinct from a verdict and `AGENTS.md` already documents. Cost: an
upstream change (filed as **claude-arsenal#168**), and consumers must not be
able to reach 'unmeasured' by simply omitting a measurement — the status has to
be asserted, or this becomes the vacuous-pass hole in a new place. Benefit: the
distinction D-2 insists on becomes expressible everywhere, not worked around
once.

**Do not resolve this by relaxing the floor, or by scoring cue-derived gold as
if a person had placed it.** Both make the number appear without making it
true, and D-2 exists because that already happened once.

## Resolution — A and B together, 2026-08-22

**B's upstream half had already landed.** `claude-arsenal#168` shipped in the
vendored bundle before this task was picked up: `gate_evidence.py` takes a
`status-key:` line and exits 3 for a metric the evidence file *positively
asserts* is unmeasured, and `gate_run.sh` propagates it as `gate: unmeasured`.
The "What the code does" section above describes the state before that.

**B alone would not have unblocked anything.** Exit 3 is still a hard stop in
two places, both by design: `open_task_pr.sh` refuses to open a PR on it ("the
task gate could not run or reports its metric unmeasured (exit 3); nothing was
verified"), and `tools/verify_gates.py` treats only `returncode == 0` as a
pass. So the third outcome makes the state *recordable*, never *terminal* —
which is right, and which is why the split is the half that moves the queue.

**So both.** T15's gate becomes `prefilter_suppressed_positives == 0`, already
`0` over 36 positives. `extraction_macro_f1 >= 0.75` becomes **T56
(`lo-6f53`)**, blocked on T25 and T26, and *that* gate carries
`status-key: extraction_status` — so the task that must wait for labels records
"not yet scorable" instead of failing.

**The check is disease-level, not instance-level.** `src/integral/task_gate.py`
reads every task on the board, not T15's: `unrecordable_task_gates` counts any
gate whose evidence holds a non-numeric value at its key with no `status-key`
to say why. Before the split it read **1 of 67** gates and named T15; after,
**0 of 68**, with one gate declaring a status key. The next task that measures
something unscorable is caught by the same number.

Only a *positively asserted* status counts. A `status-key` pointing at a key
the evidence file does not carry is a typo, not a third outcome; accepting it
would let a gate stop checking by omission — the vacuous-pass hole reopened
somewhere new.

## Tests

`test_a_task_whose_metric_is_unmeasured_is_not_reported_as_failing` — whichever
resolution is taken, the state "the extractor is not broken, the corpus cannot
yet say whether it is right" must be distinguishable from "the extractor
scored 0".
