Owner request, 2026-08-18. The open questions were put to the owner and
answered; **the four decisions below are settled** and the payload is updated to
match. What remains open is the marker choice (options 1–4 further down), which
is an ergonomics call best made with the tool in front of you.

## Decisions taken (owner, 2026-08-18)

1. **Simulated candidates are allowed, and marked as fiction.** Inventing
   answers is often the only way to exercise a step at all — waiting for a real
   run to reach step 9 makes step 9 untestable. The profile a simulated session
   produces carries a mark saying so, and nothing that reads real profiles may
   count it. This is the same discipline `verified` versus `generated` enforces
   for the shipped tax rules: a value that was not obtained the way its label
   implies must say which way it was obtained.
2. **Notes are not retractable mid-session, because they are triaged at the
   end.** A wrong note costs one line in a review list; a retraction mechanism
   costs a second silent channel whose own failures are invisible. If a note
   turns out to be wrong, it is dropped during triage like any other.
3. **The skill listing budget is to be raised, not worked around.** See S10 —
   this is now an upstream change (`claude-arsenal` issue #143), because
   `LISTING_BUDGET_CHARS` is a hardcoded constant with no override. Test mode
   is a skill and adds to that total, so it is blocked behind the same decision.
4. **Notes are shown at the end and the owner is asked whether to address
   them** — not seeded silently, not acted on during the session. This answers
   the third open question below: print a reviewable list, ask, and seed only
   what the owner confirms. The end-of-session pass is therefore a required
   part of the feature, not an optional convenience: a note captured and never
   surfaced is the failure mode this whole design is trying to avoid.

## What it is for

Once the tool runs end to end, the way to improve the thirteen step skills is to
run a real session and notice, in the moment, where the protocol was wrong: a
question that should have been asked, a follow-up that was missed, a tone that
landed badly. Those observations are worth most while the conversation is live
and worth nothing if writing them down derails the conversation.

So: a second channel, open during a session, carrying notes **about the tool**
while the first channel carries the session **as a candidate would experience
it**.

## The requirement that drives everything

**The session must proceed exactly as a real one.** The moment the tool
acknowledges a note, adjusts its next question, or apologises, the run stops
being a test of the skill and becomes a test of the skill plus a correction. A
note is captured silently and changes nothing until the person says otherwise.

That is also what makes silent capture dangerous: a note that is mis-parsed or
missed is invisible by design. Whatever the mechanism, there must be a way to
**see what has been captured without leaving the session** — a note that
vanished quietly is worse than one that interrupted.

## The owner's proposal, and the problem with it

Proposed: everything in `[...]` is meta. Session continues without mentioning
it; `[... Let's address it now]` opts into acting immediately.

**The collision is the problem, and it is not hypothetical.** This tool's main
input is pasted job adverts and CV text. Adverts are full of brackets —
`[Remote]`, `[Barcelona]`, `[sic]`, bracketed section headers. A candidate
pasting an advert containing brackets would have part of it eaten as meta, and
under silent capture they would not be told. The one surface that must never be
corrupted is the pasted advert: T11 keeps `text` byte-for-byte verbatim because
extraction evidence spans are offsets into it.

A second, smaller problem: the proposal puts two different things in one
channel — an observation ("you should have asked X") and a control instruction
("address it now"). They want different handling and probably different markers.

## Options to decide between

1. **A rarer sigil** — `[[...]]` or `((...))`. Keeps the inline feel, collides
   far less than single brackets. Still collides in principle.
2. **A slash command per note** — `/note <text>`. No collision at all, but
   heavier to type mid-flow, and the command surfaces in the transcript.
3. **Sigil plus a guard**: `[[...]]` inline, *and* meta parsing suspended while
   the turn is a paste (long text, or explicitly `/paste`). Best of both, more
   machinery.
4. **A separate channel entirely** — notes go somewhere that is not the
   conversation. Cleanest semantics, worst ergonomics, and the owner explicitly
   wants to type inline.

**Recommendation to argue about:** (3) — `[[...]]` for a silent note, `[[! ...]]`
for "act on this now", and no meta parsing inside a paste. Separating the
*observation* from the *instruction to act* means the end-of-session pass can
treat every silent note uniformly.

## Constraints that are not negotiable

- **A test note is never candidate evidence.** It is a fact about the tool, not
  about the person. It must not reach `profiles/<handle>/evidence.jsonl` or any
  derived file — the same reasoning that put the decline ledger in `session/`
  rather than the evidence log (T40). A session used for testing must still
  produce a clean profile, or the test corrupts its own subject.
- **Capture the step that was live when the note was made.** Session state (T35)
  and the step runtime (T34) already know it. A note reading "should have asked
  about qualifications" is actionable when attached to step 3; without it,
  somebody has to reconstruct where the conversation was.
- **Notes become queue tasks, but only ones the owner confirmed.** Their whole
  value is improving the skills, and this repository's way of turning a finding
  into work is a task with a gate. Decision 4 settles the mechanism: the session
  ends by printing every note with the step and skill named, asks which to
  address, and seeds only those. Seeding all of them silently would fill the
  board with observations that were wrong or already known.
- **Entering test mode is explicit and visible in the record**, so nobody later
  mistakes a test session's artefacts for a real candidate's.

## Open questions — answered

All three are settled above (decisions 1, 2 and 4). Recorded here with their
answers rather than deleted, so the reasoning is visible when somebody
implements against this payload:

- **Simulated candidates?** Yes, marked as fiction, and excluded from anything
  that reads real profiles.
- **Retractable mid-session?** No — triage at the end covers it.
- **Seed automatically or print a list?** Print, ask, then seed what is
  confirmed.

**The marker is settled (owner, 2026-08-20): option 3, the recommendation.**
`[[…]]` is a silent observation, `[[! …]]` is one to act on now, and meta
parsing is suspended inside a paste — an explicit `/paste` turn, or one at
least `PASTE_CHARS` long. The machinery the option costs is what makes the
silence auditable rather than merely silent: every marker the guard declines is
counted (`unparsed_markers`), every `[[` that never closed is counted
(`unclosed_markers`), and both are printed in the end-of-session review. A note
that vanished quietly is worse than one that interrupted, so the mechanism that
could lose one has to say how often it did.

## Review findings folded in (Qodo, 2026-08-20)

Nine of eleven were real and are fixed here. The four worth remembering,
because each is the feature's own failure mode turned inward:

1. **The loss counters lived in process memory.** `query_notes.py` runs in a
   different process, so the documented triage command reported zero lost
   markers however many had been eaten, and exited 0 — silent capture's
   invisible failure, reproduced inside the mechanism built to expose it. They
   are ledger rows now (`TallyRow`), and every reader gets them from the file.
2. **A reopened session restarted numbering at 1.** Two notes numbered 1 make
   `--seed 1` ambiguous, and `seed_specs` selects every row whose number was
   confirmed. `MetaChannel` resumes from the ledger's highest `n`.
3. **`[[! …]]` had no door.** `feed` returns only the visible text, which is
   what keeps silent notes silent — but it meant the documented act-now
   exception was unreachable at runtime. `pending_actions()` exposes the last
   turn's act-now notes, and only those.
4. **A simulated profile could not be resolved.** `resolve_handle` reads the
   roster, which now excludes fiction, so the invented candidate was
   unreachable even by name and could not enter the step flow it exists to
   exercise. `include_fiction` is threaded through, off by default.

Also: the seed command carries `--body` (it was dropping the note's full text
and step attribution into an empty body), and two session ids that slug alike
no longer share a ledger — the digest of the raw id is appended.

## Acceptance gate

A test-mode session captures every meta note with its live step, changes nothing
in the visible conversation, writes nothing into the candidate's profile, ends
by showing every captured note and asking whether to address it, and — for a
simulated run — leaves a profile marked as fiction that no real-profile reader
counts.

```bash
uv run pytest tests/test_test_mode.py -q
uv run python -m jobsearch.test_mode --check
```

```gate
test_notes_reaching_candidate_evidence == 0
evidence: status/evidence/S11.json
key: test_notes_reaching_candidate_evidence
```

## Tests

`test_a_meta_note_never_reaches_the_evidence_log` — the constraint above, and
the one whose failure is invisible;
`test_a_pasted_advert_containing_brackets_is_not_eaten` — driven by a real
corpus ad, since the corpus is the thing at risk;
`test_the_visible_conversation_is_byte_identical_with_and_without_notes` —
what "changes nothing" has to mean to be testable;
`test_a_note_records_the_step_that_was_live`;
`test_notes_survive_to_the_end_of_the_session_and_are_recoverable`;
`test_every_captured_note_appears_in_the_end_of_session_review` — decision 4,
and the one that catches a note parsed but silently dropped, which silent
capture makes invisible by construction;
`test_nothing_is_seeded_until_the_owner_confirms`;
`test_a_simulated_profile_is_marked_fiction_and_excluded_from_real_readers` —
decision 1; the exclusion is asserted from the reader's side, because a mark
nothing checks is decoration.

## Location

`src/jobsearch/test_mode.py` (new), `.claude/skills/test-mode/` (an orthogonal
mode skill, written through `skill-creator`), `tests/test_test_mode.py` (new),
and `src/jobsearch/identity.py` — where the fiction mark is *read*.

Depends on S7 (the step skills it exists to improve) and reads T34/T35.
S10 is settled (13,000-char declared budget, 862 chars spare after this skill),
so decision 3's block is discharged rather than worked around.

**Two placements are load-bearing, and both are one step stricter than the
payload asked for:**

* the note ledger is at `<profiles root>/.test-mode/<session id>.jsonl` —
  **outside every profile tree**, not in the candidate's `session/`. It cannot
  reach a derived file because it is not inside a candidate; it exists before
  identification does, so a step-0 note has somewhere real to go instead of an
  in-memory buffer a crash would empty; and the leading dot means
  `list_identities` already skips it;
* the fiction mark is a field on `Identity`, and `list_identities` excludes it
  **by default**. Every existing reader stops counting fiction without being
  changed — the opposite of a flag each caller must remember to check.
