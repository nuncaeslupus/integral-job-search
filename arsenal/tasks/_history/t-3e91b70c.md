## Why this exists

The account spent its **2000 monthly GitHub Actions minutes in four days** and ran
dry on 2026-09-04. Runs still start and still fail, in single-digit seconds with
unreadable logs. `merge-policy` is `after-ci-and-review`, so half the policy has
no enforcer until the period turns over.

`make host-gate` runs exactly the four checks CI ran, which makes it the obvious
stand-in. Run in a session's own checkout it answers a **weaker question**:

- CI measured the **pushed commit**. A local run measures the working tree, which
  can carry uncommitted edits, a staged-but-uncommitted file, or a stale `.pyc`
  whose source was restored inside the same second — see `CLAUDE.md`, "A reverted
  mutation can leave the mutated bytecode running", which is a real trap met on
  #329.
- CI's verdict named the commit it tested. A local verdict is whatever the session
  says it is. On 2026-09-04 the tested-equals-merged property was checked **by
  hand, twice**, on #329 and #319 — exactly the kind of step that gets skipped the
  third time.

## Scope

- `tools/verified_gate.sh` — resolve a ref to a 40-character SHA, check **that
  commit** out into a throwaway detached worktree, clear bytecode, run
  `make host-gate` there, print a verdict block naming the commit, remove the
  worktree.
- It **delegates** to the aggregate target and never lists targets. A listed
  subset is a second definition of the gate, free to fall behind the Makefile,
  which is D-22's subject one layer out.
- `integral.verified_gate` asserts the script still does all of that, and that
  `CLAUDE.md` names it. Prose naming no script, and a script no prose names, are
  the two halves of D-22's original defect.
- Fix the trigger that made every pull-request push run the whole suite **twice**
  (`on: push: branches: ["**"]` beside `on: pull_request`, in concurrency groups
  that cannot collapse because `github.ref` differs between the two events).

## The zero must hide nothing

`verified_gate_defects` is a sum, so each component is reported beside it by name:
`host_gate_targets_not_run`, `missing_properties`, `undocumented`. A metric reading
0 while a reader cannot see *which* properties were checked is the shape this
repository has caught four times — `status_is_asserted` (T108),
`incidental_duplicate_drops` (#323), `negation_recall_hits_by_mechanism` (#318),
`robots_adjudications_without_a_competent_second_reader` (T116).

The denominator is a floor, `verified_gate_properties_at_least`, and it is compared
against the declared table rather than written as a literal that can drift from it.

## A grep is not a proof

The module reads the script's text; text cannot tell you the script works. So
`tests/test_verified_gate.py` runs it — against a throwaway repo whose committed
gate passes and whose **working tree is then dirtied so a local run would fail**.
The script must still report PASS, and must name the commit. Plus: a failing gate
must fail, an unresolvable ref must refuse rather than measure something else, and
no worktree may survive.

Running it against *this* repository would take four minutes and prove only that
this tree is green, which `make host-gate` already says.
