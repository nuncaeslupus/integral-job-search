Imported from issue #308

Found by CodeRabbit on #304, which flagged that T101's row was unticked while T103 depends on it and is complete.

The pair really was contradictory, but the drift was not T103's. **52 of 125 archived-merged tasks still carried an unticked row** in `status/plan.md`, plus one ticked in the other direction (T15). Swept on `main` in `e32a541`; this is the check so it cannot recur.

> **The filed figure was 47 of 123 and the title still carries it.** 47 is what
> the sweep in `e32a541` *ticked*, not what had drifted: re-measuring its parent
> (`e32a541~1`) with this checker finds **52 unticked over 125 compared**, and the
> sweep left **five** behind — S8, T5 and T52 as `◐`, T20a and T26b as `☐`. So the
> sweep was itself incomplete, which is the argument for a gate rather than a
> sweep, made by the sweep. The title is left as filed because it quotes issue
> #308 and is the join key the board resolves issues to task files by; the number
> is corrected here, in `plan_v2`'s module docstring, and nowhere else claims it.

## Why it happens

Nothing ties the tick to the archive. `open_task_pr.sh` moves the task file into `arsenal/tasks/_history/` with `status: merged` in the same diff, and `integral.plan_v2` checks the label, the gate form and plan/queue agreement — but no one checks the box. The two records simply drift apart, silently, one merge at a time.

## Why it matters more than bookkeeping

`status/plan.md` is what a session reads to see where the project is. A board that reports 44% of its finished work as unfinished is not a status document, it is noise — and the failure is the one this repository keeps legislating against: a record that quietly stops describing what it claims to describe, while every gate stays green.

## Scope

Extend `integral.plan_v2`: every task with a file in `arsenal/tasks/_history/` carrying `status: merged` must have a ticked row, and the converse — a ticked row whose task is still live in `arsenal/tasks/` is the same fault the other way round. Report it as a counted metric with a denominator, not a boolean.

`plan_v2` already resolves labels to task files for `plan_queue_task_drift`, so the join exists; this is a second assertion over the same pairing.

Do this **after** `e32a541`, or the check lands red on 47 rows.

## Gate

`merged_tasks_with_an_unticked_plan_row == 0`, denominated by the number of terminal tasks compared, with a floor so a scan that finds no archive reports `unmeasured` rather than a clean zero.

## What was built

A fourth drift dimension in `src/integral/plan_v2.py`, over the pairing the module already
resolves for `plan_queue_task_drift`, recorded in `status/evidence/S8.json`:

- **`merged_tasks_with_an_unticked_plan_row`** — the gate. For every task the board reports
  as `merged` (a file in `arsenal/tasks/_history/` carrying `status: merged`), the plan row
  for its label must read `☑`.
- **`ticked_rows_without_a_merged_task`** — the same fault reversed: a row claiming a
  completion the archive does not have. T15 carried one, ticked while its task file sat
  `open` in `arsenal/tasks/`.
- **`merged_tasks_compared`** — the denominator, committed as
  `merged_tasks_compared_at_least: 100` and never as the count of the day, for the reason
  `status/evidence/T100.json` records about `files_scanned`: archiving the task file is
  precisely what a task PR does, so an exact value is wrong on one side of every archive.

**The direction is the whole point.** The archive decides what is merged and the plan row is
then required to agree; nothing here reads a tick to decide what is merged. A check derived
the other way round would be satisfiable by editing the document it is checking, which is the
failure mode, not an implementation detail — `test_the_tick_check_reads_the_archive_and_never_the_plans_own_ticks`
runs one plan against two boards and asserts the verdicts differ.

**A merged task with no plan row at all counts as unticked.** "There is no box, so nothing is
unticked" is the fail-open reading, and it would make the metric satisfiable by deleting the
row rather than ticking it. `plan_queue_task_drift` reports the same task from the membership
side and both must, because either could be relaxed on its own.

**`◐` is not a tick and `☒` is not required to be one.** The plan's own legend reads
☑ merged · ◐ in progress · ☐ open · ☒ cancelled. Three of the nine rows this landed with had
drifted to `◐` rather than to `☐`; reading it as close enough is how they stayed invisible.

**An archive that resolves nothing is `unmeasured`, and that is not excused.**
`merged_tick_status` reads `unmeasured` and the metric reads `-1` rather than a clean `0`, so
the gate `== 0` still fails; `merged_tasks_compared` is additionally floored at 100, so
`main` exits 1 and `write_evidence` writes nothing at all. No `status-key` is declared on the
gate block deliberately — a gate that excuses itself when it could not measure is the
fail-open direction, and this one goes red instead.

**The backfill: nine rows.** Eight archived-merged tasks were unticked (S8, T5, T20a, T26b,
T52, T57, T89, T94 — three of them `◐`) and T15 was ticked while still open. Not the filed 47:
those were ticked on `main` in `e32a541` before this task started, and these nine are the
drift that accrued after it, which is the point — 47 was one snapshot of a leak, not its size.

## The consequence for every task PR after this one

Ticking the plan row is now part of archiving a task. A PR that moves its task file into
`_history/` and leaves `status/plan.md` alone turns `make evidence` red, by construction —
that is the enforcement, and the fix on such a PR is to tick the row, never to relax the check.

## What the second reader found, and what was done about it

An independent session read this diff and reproduced every claim in it; a third
reproduced the reproduction. Everything above holds as stated. **Eight things it
did not handle** are recorded here — seven fixed, one pinned open with fixtures
and a written record — because a report that is read and waved through leaves the
code exactly as unprotected as it was, and the next regression re-opens the same
hole with nothing to catch it.

### The metric can be zeroed by demoting a record, and that hole is left open

**Demoting an archived task from `status: merged` to `status: done` drops it out
of the numerator *and* out of the denominator, and nothing fires.** Measured on
the merged tree:

```text
baseline                                    metric 0   converse 0   compared 134   exit 0
T94's plan row unticked                     metric 1   converse 0   compared 134   exit 1
…and t-506d8fa5.md demoted to `done`        metric 0   converse 0   compared 133   exit 0
```

The third line is the fail-open one: `violations: []`, `plan_queue_task_drift: 0`,
and the denominator's fall from 134 to 133 is absorbed silently by a floor of
100. The word being changed sits in the front matter of the file the PR is
archiving, so this is reachable **in the same commit** — which is precisely the
shape this task exists to refuse ("a check derived the other way round would be
satisfiable by editing the document it is checking"). It matches the letter of
the Scope above, which says `merged`; it does not match the argument.

`_TERMINAL = {"done", "merged"}` already exists in the module and the dependency
check uses it, so widening the numerator is a two-word change — **and it cannot
be made here**, because it forces a decision about `status/plan.md` rather than
about the checker. The plan's legend is ☑ merged · ◐ in progress · ☐ open ·
☒ cancelled, with **no glyph for `done`**. Widening would demand that every
archived-`done` task be ticked as *merged* — a false statement in the document —
or that the legend grow a fifth glyph, which is the owner's call about a document
this task was not scoped to edit.

So the scope is pinned rather than widened, both directions of it:

- `test_an_archived_done_task_is_outside_this_checks_scope` asserts what the
  narrower reading does — 0 in the numerator, 1 in the denominator, no
  violations — and goes red the moment anyone widens it. Verified: replacing
  `== "merged"` with `in _TERMINAL` fails that test **and**
  `test_the_committed_plan_and_queue_agree`, i.e. the shipped board.
- `test_a_ticked_row_over_an_archived_done_task_is_not_reported_either` records
  that the *converse* metric is already strict about `done`, so the asymmetry is
  visible and widening one direction without the other is caught.

**The residue this leaves, named rather than fixed:** T29
(`arsenal/tasks/_history/lo-2293.md`) is `status: done`, archived, and
`status/plan.md:224` shows `◐` — the plan asserts a finished task is *in
progress*. It is the same class of defect this task was filed about, surviving
only because the check keys on `merged`. It is not ticked here: `☑` would say
"merged", which is not true of it, and inventing a glyph is a legend change. That
is what makes widening the numerator a document decision and not a code one, and
it is why the residue is written down instead of quietly cleared.

### A duplicate ticked row masked an unticked one — fixed

`by_label` is last-wins, so the tick check read whichever row for a label was
written last. Measured: leave T94's row unticked and append a second, **ticked**
T94 row, and `merged_tasks_with_an_unticked_plan_row` reads **0**. The run still
exited 1, but through `plan_queue_task_drift` ("T94 appears 2 times in the plan")
— a *different gate key*, and this task's own argument for counting a missing row
here as well as there applies unchanged: either check could be relaxed on its
own.

It is the same fail-open shape as deleting the row, reached by adding one. The
module docstring already refuses it for label counting — "collapsing them into a
set hides a duplicated row instead of reporting it" — and the new check was
reading the collapsed mapping.

**Fixed:** the tick check reads a `rows_by_label` mapping that keeps every row,
so a merged label is compliant only when **all** its rows are ticked. Three
fixtures hold it — the masking case, the same case with the rows written the
other way round (so a first-wins collapse is caught too), and two unticked rows
counted as two findings. The real plan carries no duplicate labels, so the
shipped measurement is unchanged.

### Five smaller ones, all folded in

- **`plan_v2.py` was no longer `ruff format` clean** — two hunks this PR added,
  the `PlanRow.__init__` signature and the `status_column = (…)` ternary, both of
  which the formatter joins onto one line. `origin/main`'s copy is clean, `make
  lint` runs `ruff check` and mypy only, and CI has no format check, so nothing
  would have caught it until the next session ran `make format` and found an
  unrelated diff in their own PR. `ruff format` run over both files touched here.
  (No format check is *added*: 19 files repo-wide are unformatted today, so the
  gate that would catch this is its own task, not a rider on this one.)

- **A false docstring.** `PlanRow` claimed an absent `St` column was
  "distinguishable from a column present and blank". Both parse to `""`; renaming
  the header and blanking every cell give byte-identical output. The behaviour is
  fail-closed and loud, so the code was right and the prose was a false claim
  about a fail-open boundary. Sentence corrected, and
  `test_a_missing_status_column_and_a_blank_cell_are_the_same_verdict` now holds
  the two to one answer.
- **`_unmeasurable()` reported `ticked_rows_without_a_merged_task: 0`** beside
  three siblings reporting `-1`. A run that could not read the plan compared no
  ticks, so `0` is a clean count over a scan that never happened, in the record
  that says `unmeasured` two keys down. Now `-1`, and
  `test_a_missing_plan_records_minus_one_not_zero` asserts all four.
- **`MINIMUM_MERGED_TASKS` cited "today's 132"** — the branch's base, one merge
  stale by the time the branch was current. Corrected to 134 *and* labelled as a
  snapshot, since a count in prose rots at the same rate as a count in evidence
  and only the evidence file has a gate watching it. That is the argument for the
  floor, not a caveat on it.
- **The direction test's citation overreached** —
  `test_the_tick_check_reads_the_archive_and_never_the_plans_own_ticks`.
  It was cited as the proof that the *gate* metric is
  archive-derived, and it asserted only the converse. Demonstrated: mutate
  `merged` to be derived from the plan's own ticks — the exact circularity the
  test is cited against — and the test as shipped **passes**. It now holds three
  rows against two archives and asserts both metrics; under the same mutation it
  fails.

### The join the gate actually runs had no test anywhere

Every tick test wrote the board as a **JSONL ledger**, setting `status` by hand.
The real board is a directory, and "the archive decides" is implemented one layer
down in `taskboard.load_board`, which reads `arsenal/tasks/` with
`default_status="open"` and `arsenal/tasks/_history/` with
`default_status="merged"` — so a file's *location* is what makes it merged.
`load_board` had **zero** callers across `tests/`: every ledger test would have
passed with that mapping reversed.

Two fixtures now run against real directories on disk — one with an archived file
and a live file carrying no `status:` line at all, and one that measures, moves a
single file into `_history/`, and measures again. Verified: swapping the two
`default_status` values fails both, and the shipped board's own test with them.

### Mutation results

Each fixture was verified by reverting the behaviour it pins (or, for the pinning
fixtures, by making the change they exist to catch), showing it red and named,
restoring, and showing green. Every source file was restored byte-for-byte and
checked by sha256.

| mutation | what it changes | fixtures that go red |
|---|---|---|
| collapse duplicates to `by_label` (last wins) | the F2 fix, reverted | masking case, multiplicity count |
| take only the first row of a duplicate | first-wins instead of last-wins | row-order case, multiplicity count |
| widen the numerator to `_TERMINAL` | the scope this pins open | `…outside_this_checks_scope`, **and the shipped board** |
| distinguish an absent `St` column from a blank cell | the false docstring, made true | missing-column-vs-blank-cell |
| `_unmeasurable` reports `0` again | the F4 fix, reverted | `…minus_one_not_zero` |
| derive `merged` from the plan's own ticks | the circularity this gate refuses | the direction test **as extended** (passes as shipped) |
| swap `load_board`'s two `default_status` values | the archive/live mapping | both directory fixtures, and the shipped board |

**One trap worth writing down, because it nearly produced a false green.** The
`load_board` mutation swaps two string literals of equal total length, so the
mutated and restored files are **byte-identical in size**; the whole
mutate-test-restore cycle finished inside one second, and CPython validates a
`.pyc` against the source's *seconds-resolution* mtime and size. The restored
run therefore executed the **mutated** bytecode: three tests failed against a
working tree `git status` reported clean, and `inspect.getsource` printed the
correct source while the wrong code object ran. `make host-gate` is what caught
it. Any mutation harness here must delete `src/**/__pycache__/*.pyc` after
writing the file — every mutation above was re-run with that in place, and each
was confirmed red-then-green from a cold cache.

## Acceptance gate

```gate
merged_tasks_with_an_unticked_plan_row == 0
evidence: status/evidence/S8.json
key: merged_tasks_with_an_unticked_plan_row
```

```bash
uv run python -m integral.plan_v2 status/evidence/S8.json
uv run --extra dev pytest tests/test_plan_v2.py -q
```

The `bash` block regenerates the measurement and runs the behavioural half; the `gate` block
asserts the number in the file. Neither alone is the gate: without the first a stale evidence
file passes unchallenged, and without the second a command that exits 0 counts as a gate
whether or not it checked anything.
