## What this is

Specification v2 says the order of the steps is a default, not the mechanism:
each step declares what it reads and what it produces, and the graph of those
declarations decides whether a step can run. This is that decider, at runtime.
T30 makes the declarations machine-checkable in `spec-v2-steps.json`; this task
reads them against a live profile.

Three questions it must answer at any moment:

| question | answer drawn from |
|----------|-------------------|
| which steps may run now? | every declared input either present on disk or marked optional (`?`) |
| what is still owed? | the outputs that are missing, and the step that produces each |
| how good is what we have? | the sufficiency level — L0 handle, L1 constraints resolved, L2 traits scored and weights fitted |

`what is still owed` is what makes "where were we?" answerable, and the level is
stamped onto every ranking and shown wherever the ranking is.

## The rule that matters

**A required step must never be blocked by an offered one.** The closure
property is stated in process spec §2.5 and §3.1 and the trace is 0 → 2 → 7 → 8
→ 9. A candidate who declines Intake must still reach a ranking; if the runtime
refuses to run Constraints because `claimed facts` is absent, the promise that
any offered step may be declined is false in code however true it is in prose.

**Optional means optional at runtime, not merely in the JSON.** An absent
optional input makes a step longer, never impossible.

## Tests

Write these RED before any production code:

`test_step_without_its_required_inputs_is_never_offered` in
`tests/test_step_graph_runtime.py` — a step whose required input is missing is
absent from the runnable set; `test_declining_every_offered_step_still_reaches_a_ranking`
— the required-only trace 0 → 2 → 7 → 8 → 9 completes with all eight offered
steps declined; `test_ranking_without_weights_is_l1` — the level is computed
from what exists, not asserted by the caller.
