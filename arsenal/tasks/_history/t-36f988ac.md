The candidate's search terms survived a session only as an evidence row. The next session did not know that `agentic ai` was the thing that had worked, so the most valuable thing a search session produces — where to look next — was thrown away at the end of every one.

`Aim` was never read from disk and never written to it: its only construction in the whole codebase was the measurement fixture at `sourcing.py`.

**And the terms that were sent were the wrong shape.** `Aim.query` joined every term into one string, which every board reads as **AND**. Measured on the owner's own log: **50 of 62 recorded fetches** went out as `agentic python engineer`, asking for an advert containing all three words. The boards that AND their terms returned nearly nothing, and it read as a thin market rather than as a malformed query.

Both halves have the same fix. A term is a **phrase**; several phrases are searched one at a time and merged, which is what searching several phrases *means*. And one phrase per request is what makes an advert attributable to the phrase that found it.

**The store for the ranking already existed.** `offers/_fetches.jsonl` has recorded `{connector, url, status, items, steered, query, at, offer_ids}` per request since T126 — provenance `offers_without_a_recorded_fetch` already gates. Nothing new is written to rank a phrase; what was missing is that the `query` column held one ANDed string and could not be read per phrase at all. A second store beside it would have been the duplication, not the feature.

Ranking is by **unique contribution** — offers no other phrase returned — then by what the candidate kept, then by volume. Volume last, deliberately: a phrase returning forty adverts that three other phrases also returned has told nobody anything, and sorting by it rewards the broadest phrase every time, which is the opposite of the steer a candidate needs. A phrase that returned **nothing** stays in the ranking, because it is the row that says do not spend a run on this again — and it is exactly the row a table built by grouping results would never contain.

`kept` and `refused` read the offer statuses, and `new` counts as neither: an offer nobody has ruled on is not a rejection, and scoring it as one would rank a phrase by how recently it ran.

Eleven contracts, each **run** rather than read. `T121` and `T136` are the
standing lesson: three rounds of checking a script by searching its text were
defeated first by its own comments and then by an unused string holding every
pattern the checker looked for. So no contract here opens a source file — each
builds a store, drives the real code, and reads what came out.

Four of the eleven are the ones a green gate could otherwise have been faked
over, and all four were mutation-verified:

- re-joining the phrases into one query is caught by *one request per phrase*;
- ignoring steerability, so a board that returns its whole list is fetched once
  per phrase for one answer, is caught by *an unsteered board is fetched once*;
- counting every offer as unique is caught twice, by *unique contribution
  ignores shared offers* and by *volume does not win*;
- removing the persistence is caught by *a run records what it searched with*.

**5 of 5 mutations caught.** The persistence contract exists because writing
the aim on the caller's initiative is writing it exactly when a session ends
tidily — and a session that ends badly is the one whose terms were worth
keeping.
