## The defect

`integral.robots` — the matcher `CLAUDE.md` tells every session to adjudicate a
real board with — answers **ALLOW** for nine paths RFC 9309 refuses. They are
**one bug, not nine**:

```
User-agent: *                       request                        case
Disallow: /foo/bar?baz=https%3A%2F%2Ffoo.bar
                                    /foo/bar?baz=https://foo.bar   31
Disallow: /s?q=a%26b                /s?q=a&b                       50
Disallow: /s?q=a%3Db                /s?q=a=b                       51
Disallow: /jobs%3Aremote/list       /jobs:remote/list              61
Disallow: /r&d/notes                /r%26d/notes                   62
Disallow: /filter/size%3Dxl         /filter/size=xl                63
Disallow: /geo/lat,lon              /geo/lat%2Clon                 64
Disallow: /u/%40acme                /u/@acme                       65
Disallow: /c++/guide                /c%2B%2B/guide                 66
```

§2.2.2 states its canonicalisation over a set rather than over an example:
octets "outside the range of the US-ASCII coded character set, and those in the
reserved range defined by RFC3986, MUST be percent-encoded ... prior to
comparison" (RECOLLECTED). `:`, `/`, `&`, `=`, `,`, `@` and `+` are all in
RFC 3986's reserved range, so each rule above and its request are two spellings
of one URI, and each rule refuses. The section's example table (row two)
*illustrates* the requirement with `:` and `/`; it does not bound it. Nor does
it bound the **region**: §2.2.2 canonicalises the path *and* the query, and
RFC 3986 §3.3 admits every one of those octets inside a path segment as `pchar`,
where it is data with no delimiting purpose to conflict with.

**The cause is a single allowlist applied in two regions.** `robots.py`'s
`_CHUNK_SAFE = "/:@!&'()+,;=?~-._"` names the octets the module never
percent-encodes — `: & = + , @ ! ; ' ( )` among them — and it is consulted for
the path and for the query alike. So one constant leaves those octets unencoded
wherever they appear, and the rule and the request never compare equal. **One
fix should close all nine**; nine fixes closing one row each is the shape this
task exists to refuse.

**It is fail-open**, in the matcher that decides real fetches. The reserved
octets `_CHUNK_SAFE` exempts and no committed case yet exercises are the
untested remainder of the same hole, not a separate one.

## The count was 3 when this task was filed and is 9 now — the matcher did not regress

Read this before concluding anything from the number. The metric
`repo_matcher_verdicts_against_the_rfc` moved from **3 to 9** on T120's fourth
review round, and the move is **coverage widening, not decay in
`integral.robots`**. Nothing about the live matcher changed; no commit between
the two readings touched `robots.py`.

What changed is the second reader. Its §2.2.2 encode pass had been gated on the
query region alone, so the independent case table could only ever ask the
question about a query. Widening that pass to the whole path let six new
spec-derived cases (61–66) be written, and those six find the *same*
`_CHUNK_SAFE` allowlist one region over. The implementing session measured the
control explicitly: **with the region fix applied and the table still at its 59
rows, this set was still exactly the three original ids.** The six are new
questions, not new failures.

The number could also have been held at 3 by testing only `$` — the one reserved
octet absent from `_CHUNK_SAFE`, so a table built from it alone would have kept
the pin stable while proving strictly less. That route was refused, on this
repository's rule that a metric reports the truth rather than a comfortable
number.

## How it was found, and why the finding is committed rather than fixed

T120 replaced the *second* reader and, in doing so, bought a case table derived
from RFC 9309 by a session that had not read `src/`. Running that table against
`integral.robots` as well as against the new reader costs nothing, and the
49 rows it opened with produced exactly one disagreement. Fixing the primary
matcher was not T120's job, so what T120 shipped is the proof plus a pin:

* `second_reader.REPO_MATCHER_DISAGREEMENTS` names each case, so a **new**
  disagreement appearing fails a test by name rather than moving a count;
* `status/evidence/T120.json` commits `repo_matcher_verdicts_against_the_rfc`.

**The pin then fired twice on T120's own pull request, and that is why this task
is scoped to the rule rather than to the row.** The first firing: the
independent read found the same shortcut in the *new* reader —
`_QUERY_DATA_OCTETS = ":/"`, the two octets the example table happens to print —
and derived cases 50 and 51 from §2.2.2's text against it, taking the count from
one to three. The second firing is the region widening described above, which
took it from three to nine. Each time the finding generalised, and each time the
answer was to widen the scope rather than to trim the table.

The pre-PR review's objection to stopping there is this task's reason to exist:
a pin with no expiry is a permanent green test asserting that a known fail-open
is still present, and this repository's rule is that an accepted finding is
committed *and owned*, not read and waved through.

## Scope

* **Reserved octets used as data, in the path as well as the query** — not `:`
  and `/`, and not the query alone. Canonicalise every octet in RFC 3986's
  reserved range that appears as data in either region before comparison. A fix
  that adds `:` and `/` to some encode-here list and stops has fixed the rows
  the table happens to carry and left the remaining reserved octets exactly as
  fail-open as they were; a fix that treats only the query leaves six of the
  nine standing. Both are the defect this task was re-scoped away from, and the
  second is the defect T120's own reader shipped with until its fourth round.
* **Expect one change, not nine.** `_CHUNK_SAFE` is a single allowlist consulted
  in both regions. A diff that patches the query region and the path region
  separately is evidence the cause was not found.
* Say in the code what is **held out** and why, because that is the part a list
  cannot express. `*` and `$` carry §2.2.3 pattern meaning; the query's opening
  `?` is what makes "in the query" decidable at all; and `/` is RFC 3986 §3.3's
  segment separator, which must **not** encode in a path even though every other
  reserved octet there must — case 67
  (`a_path_separator_is_not_data_beside_one_that_is`) is the control that stops
  the fix being "encode every reserved octet", and it is currently green. Those
  exemptions are reasoned and read **per region**, not per octet; every other
  one is a hole.
* `integral.second_reader.canonical` already implements one reading of this
  (its encode pass, plus the spellings that resolve a rule reaching the query
  through a wildcard). **Do not copy it.** The two matchers are worth having
  because they were derived independently; a `robots.py` written from
  `second_reader.py` is one matcher with two names, which is the exact failure
  T120 exists to have removed. Derive it from §2.2.2 and RFC 3986's `reserved`
  production instead.
* When it lands, `repo_matcher_verdicts_against_the_rfc` reads 0 and
  `REPO_MATCHER_DISAGREEMENTS` empties — the test that pins the set asserts both
  directions, so an empty pin over a non-empty finding fails too.
* T70's `robots_verdicts_misread` must stay 0: this changes canonicalisation, and
  that is the gate which exists because percent-encoding equivalence took ten
  defects across five review rounds.
