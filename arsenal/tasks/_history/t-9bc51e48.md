T133 gave a connector a `client`; T130 gave sourcing a detail fetch. They were never joined: `_detail_record` built its request with `headers={}`.

Measured live on 2026-09-06, immediately after T134 shipped `foorilla_en`:

    foorilla_en  items=50  added=0  detail_fetched=40

Fifty rows parsed, forty advert pages fetched, **zero offers**. The fetches answered **200** — with the site's 10,836-byte shell, because foorilla serves the advert only to an htmx request too. The detail selectors matched nothing and every row was dropped for "no text", which reads as a connector whose selectors are wrong rather than a request missing two headers.

The headers come from `connector.detail`, not from the listing: a board behind htmx targets a different element for each surface, and foorilla uses `mc_1` for the list and `mc_2` for the advert. A mutation sending the *listing's* headers to the advert page is caught for that reason.


## Acceptance gate

```gate
boards_starved_by_a_missing_detail_fetch == 0
evidence: status/evidence/T126.json
key: boards_starved_by_a_missing_detail_fetch
```

T130's gate, which is the right one: a board whose listing parsed rows and
yielded no offer, while its connector declares a `detail:` page, is a board
this engine starved. Sending the advert page no headers starves it exactly as
not fetching the page at all did — the fetch merely returns 200 first, which is
what made it invisible.

The narrower property is pinned by
`test_the_advert_page_gets_its_own_clients_headers`: the listing request
carries `HX-Target: mc_1` and the advert request `mc_2`, both read from the
committed `foorilla_en` package. **2 of 2 mutations caught** — sending no
headers, and sending the *listing's* headers to the advert page, which is the
plausible wrong fix and is wrong for a board that targets two elements.
