Owner check after the test session of 2026-08-20: of the seven offers sourced, the two jobtoday.com
listings return **403** and every tablondeanuncios.com listing reads **"Puesto ocupado"**. Not one was
a live vacancy. They were surfaced by a generic `WebSearch` over indexed pages, which is exactly the
failure mode: a search index outlives the advert.

Owner's rule, to encode: **real searches are run inside the portals**; a generic `WebSearch` is for
*discovering new portals*, not for collecting adverts.

What this needs:
- sourcing must fetch the detail URL and treat 403 / "puesto ocupado" / "oferta cerrada" as expiry,
  not as an offer;
- `integral.freshness` already exists — wire it into the sourcing path and mark dead ones expired;
- `step-07-sourcing` prose must forbid presenting a search-index result as a live offer.

Addressed in: `step-07-sourcing`, `src/integral/liveness.py`. *(As filed this line named `src/integral/freshness.py`; that module is T36 and unrelated — see "What was built". `offers.py` needed no change: `OfferStatus` already had `expired`.)*


## What was built

**`src/integral/liveness.py`, not `integral.freshness`.** The task proposed wiring the existing
`freshness` module into the sourcing path. That module is T36 — proactive re-entry, deciding whether
to ask a returning candidate what has changed since — and its `Offer` is a question the tool would
like to ask, not a job advert. The two share a word and nothing else; wiring it in would have done
nothing. Advert liveness got its own module, whose docstring says so plainly so the next reader does
not repeat the trip.

**Three verdicts, where the task named two.** `live`, `dead`, and `unverified`. The task said to treat
403 as expiry; the operative half of that instruction is *"not as an offer"*, and both `dead` and
`unverified` achieve it. But a 403 is an anti-bot rule and a filled vacancy, indistinguishable from
outside — recording it as `dead` would tombstone a vacancy that may be perfectly open, and a tombstone
is what stops it ever being offered again (§7.4). So a 403 withholds without claiming to know why.
**Flagging this as a deliberate departure from the filed instruction**, not an oversight.

**What may be presented is what was checked and found alive** — not "what was not found dead". An
offer with no check at all is withheld on the absence, because the absence is the defect.

**`step-07-sourcing` carries the rule**: real searches run inside the portals, a general web search is
for discovering portals, and the withheld count is said out loud rather than hidden.

## What measures it

`offers_presented_without_a_liveness_check` probes every arrival shape that session produced — a
search hit nobody fetched, a 403, a body reading "puesto ocupado", a 404 at a board — plus the one it
never managed: an advert fetched and open. Each must land on the right verdict, be withheld or shown
accordingly, and be expired only when actually dead.

The live scenario is required for the measurement to count at all: without it the check could pass by
withholding everything, which is as useless to the candidate as showing them seven dead adverts.

Confirmed against the pre-D-18 behaviour: with `unverified` treated as presentable — which is what
"nobody checked, so show it" amounts to — the count goes to 2, naming the search hit and the 403.

## Left for someone else

**Nothing fetches yet.** This module decides a verdict from a response; the sourcing path still has to
make the request and feed it in. That is the wiring, and it needs the egress the connector work (T12)
is waiting on. Recorded rather than pretended: the rule and its measurement exist, the fetch does not.

**The phrase list is Spanish-and-English and hand-kept.** Nine phrases from the boards this candidate's
market uses. A board that says it differently will read as live, which is the failure mode to watch —
`dead_phrases_known` is in the evidence so the number is at least visible.
