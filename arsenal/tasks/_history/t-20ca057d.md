Found during the test session of 2026-08-20.

`run_checkpoint.py --id perico` for step 9 (`ranking`) printed:

    {"step": "ranking", ..., "coverage_met": true,
     "gate_metric": "explained_fraction == 1.0", "gate_owner": "T19",
     "gate_state": "not_implemented"}

and exited **0**. The script named the gate, said out loud that it does not exist, and let the
session continue. The same held for step 8 (`extraction_macro_f1`, `not_implemented`), where
`extract()` had settled 0 of 25 dimensions on every advert.

This is the inert-gate problem from `claude-arsenal/AGENTS.md` — "a gate that runs nothing passes
everything" — one level up: a *step* whose gate is unbuilt still reports the machine-visible half of
its stop rule as met. `coverage_met` answers "are the artefacts present", which a step can satisfy by
writing files nobody checked.

Decide deliberately between:
- exit non-zero on `gate_state != implemented` (a step with no gate cannot be certified), or
- keep exit 0 but require the step skill to say the gate is unbuilt before presenting its output.

What must not stand is a clean exit that reads, to a caller, as "this step passed".

Addressed in: the shared `run_checkpoint.py` (all thirteen step skills), `src/integral/step_gates.py`.


## Acceptance gate

```gate
steps_certified_on_an_unimplemented_gate == 0
evidence: status/evidence/D-21.json
key: steps_certified_on_an_unimplemented_gate
```

```bash
uv run python -m integral.step_certification --write-evidence status/evidence/D-21.json
uv run --extra dev pytest tests/test_step_certification.py tests/test_step_gates.py -q
```

The `bash` block regenerates the measurement and runs the behavioural half; the `gate` block
asserts the number in the file. Neither alone is the gate: without the first a stale evidence
file passes unchallenged, and without the second a command that exits 0 counts as a gate
whatever it measured.

## What was decided

**Both resolutions, because they answer different readers.**

`integral.step_gates.checkpoint_exit` is now the one place a step checkpoint's exit code is
decided, and it refuses to return 0 for a step whose gate is unbuilt — the first resolution.
The code is **3**, not 1: reusing 1 would have made "this step has no gate" indistinguishable
from "this candidate has not finished the step", and that ambiguity is precisely what let the
defect go unnoticed. `coverage_met` keeps its meaning — the artefacts really are present, and
saying otherwise would be a lie in the opposite direction — and a new `certifiable` field, from
which the exit code is derived, carries the answer the caller was actually reading 0 as.

The second resolution is the half a person reads rather than a caller: each of the seven step
skills whose gate is unbuilt now says so in its own `## Checkpoint` section, and is required to
say it before presenting the step's output.

## What measures it

`steps_certified_on_an_unimplemented_gate` counts, over all thirteen steps, the checkpoints that could still
reach exit 0 without asking `checkpoint_exit` — read off each script's AST, plus the skills
whose prose disagrees with their recorded gate state. A script or `SKILL.md` that cannot be
read counts toward the number rather than being skipped, so a broken probe cannot produce a
clean zero.

The reading lives in `src/integral/step_certification.py`; the *running* — each of the thirteen
scripts driven through its own `main` with `checkpoint()` stubbed — lives in
`tests/test_step_certification.py`, because
`test_nothing_in_the_codebase_executes_a_contributed_parse_module` forbids `integral` from
loading code out of a path, and the connector contract's safety argument rests on that.
Both halves were confirmed to fail against the pre-D-21 tail before being trusted.
