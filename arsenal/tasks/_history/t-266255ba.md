Transcribed from `status/plan.md`'s row for this task, which declared this
metric before the task was imported. The name is the plan's, not a new one:
inventing a second name for a declared metric is a mistake this repository has
made four times, and `test_the_committed_plan_and_queue_agree` fails it.

Imported from issue #302

Found by the second-reader audit of #295 (T89), and disclosed in that connector's own `still_open`. Filing so it is not left to the disclosure alone.

The ledger's measured curl body is `{"Keyword":"python","ResultsPerPage":25}`, and `probe/captured.json` records that request. The shipped `connectors/usajobs_en/connector.yaml` sends a **third** key, `Page: "{page}"`, which no capture and no retest ever exercised.

`Pager.CurrentPageIndex` was read *out of the response*, which shows the board **reports** a page index — not that it **accepts** one in the request under that name.

It is inert today at `max_pages: 1`. It stops being inert the moment anyone raises that.

## What would settle it

One curl with `"Page":2`, checking the rows differ from page 1, recorded in `probe/`. Then either the key is measured and `max_pages` can rise, or it is dropped and `pagination.mode` goes to `none` until someone measures it.

**If the board ignores an unknown `Page` key, page 2 is a duplicate of page 1 and the fetcher collects duplicate offers** — which dedup may or may not catch, and which nothing would report.

## Resolved: the key is dropped, and the rule is checked library-wide

Only one of the two branches above was open. The measurement that would settle
`Page` needs a live POST carrying `"Page": 2`, and a capture invented in its
place is the defect this task is about — so `Page` is gone from
`connectors/usajobs_en/connector.yaml`, `pagination.mode` is `none`, and
`probe/captured.json` now records the request it was taken with (`method: POST`
and the body `{"Keyword":"python","ResultsPerPage":25}`) so that the absence is
checkable rather than inferred.

`integral.pagination_capture` is the rule, applied to every shipped package: a
page key a package sends must appear in a **recorded request** — the captured
URL's query string under `query_param`, the captured body under `body_field`,
the captured URL itself under `path_segment`. Nothing reads a response, which
is the distinction the whole task rests on.

The scan found a second instance the filing did not know about. `pythonorg_en`
issued `?page=1` and `?page=2` while `probe/captured.json` records
`https://www.python.org/jobs/` — neither URL it sent had ever been fetched. Its
page-2 measurement was made and is written out in the package, but a dated
sentence in a comment is not a capture, so it is resolved the same way and the
connector's URL is now the one that was actually captured. One commit of a
`?page=2` capture restores it; the same is true of usajobs.
