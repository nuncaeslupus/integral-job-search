Measured live on 2026-09-06 against six installed connectors.

`_one_board` (src/integral/sourcing.py:238) fetches only list pages. `_offer_from` then requires a `text` field, and a connector that legitimately declares `text` on its **detail** page — because the list row carries no teaser — produces zero offers while reporting a clean 200 with items parsed.

Live counts from one pass:

| connector | rows parsed | offers added |
|---|---|---|
| arbeitnow_en | 35 | 0 |
| usajobs_en | 25 | 0 |
| trabajos_es | 40 | 16 (24 dropped) |
| getmanfred_es | 22 | 0 |
| wellfound_en | 20 | 0 |
| remotive_en | 18 | 0 |

~130 adverts per pass, discarded by the engine, not by the boards.

This is one defect, not six. `connectors.py` already carries the whole detail
layer — `parse_detail_page`, `detail_url_template`, `detail_url` on every list
item (LIST_FIELD_NAMES). Nothing in `sourcing.py` calls any of it.

Related and separate: `arbeitnow_en/connector.yaml` documents 'No `text` here on
purpose: a list row carries no teaser or description', which is correct — the
connector is right and the engine is wrong.

## Scope

Fetch an item's `detail_url` when the list row cannot complete an offer, parse it
with `parse_detail_page`, and merge. Robots must be adjudicated per detail URL
exactly as it is per list URL. Cap the per-run detail fetches so one board cannot
turn a listing pass into hundreds of requests.


## Acceptance gate

```gate
boards_starved_by_a_missing_detail_fetch == 0
evidence: status/evidence/T126.json
key: boards_starved_by_a_missing_detail_fetch
```

A board whose listing parsed rows, yielded no offer, and whose connector
declares a `detail:` page carrying the rest is a board **this engine** starved —
not a board the market emptied. Measured over the committed fixtures, which now
serve each package's `fixture/detail.html` as well as its `fixture/list.html`.

It lives in `T126.json` rather than a file of its own because it is a property
of the same fixture run T126 already measures, and a second run of the same
thing is a second thing to keep in step.

**The denominator is asserted, not assumed.** `boards_needing_the_advert_page`
counts boards whose listing actually sent us to an advert page, and a run where
that is zero reports `gate_status: unmeasured` instead of a clean zero.
Verified by deleting the detail fetch: the count stays 0 and the status turns
`unmeasured`, so the mutation cannot pass the gate by emptying it — which is
the exact shape T127 found from the other side, a check whose two sides carried
the same offers and measured nothing.
