`status/evidence/T125.json` commits `files_checked` as an exact value — 453 at
the time of writing — and it is the count of every file `ruff format` touches.
Since ruff 0.16 that includes **Markdown**: `ruff format --check` on a single
task file reports `1 file already formatted`. So the number moves on any pull
request that adds a `.md`, and `arsenal/tasks/` alone contributes 189 of it.

Met on the pull request that seeded T141–T149. Nine task files, no Python
touched at all, and `make evidence` went red with `453 -> 462`. Regenerating and
committing the new value is not a fix: the next task PR moves it again, and the
one after that. A gate that goes red for a reason unrelated to what it measures
teaches sessions that red is normal, which is the failure `make host-gate` exists
to prevent.

**This is T100's finding, in a key T100 did not reach.** T100 replaced T55's
exact `files_scanned` with the floor `files_scanned_at_least` for precisely this
reason — a denominator exists to stop a clean zero resting on an empty scan, and
a floor does that job without moving. `T100.json`'s
`archive_sensitive_evidence_keys` compares the committed record across a
simulated **archive**, which is why it never saw this one: adding a file is not
archiving a file, and `files_checked` drifts on the first and not the second.

So there are two pieces, and the second is the one that matters:

- **`files_checked` becomes a floor**, `files_checked_at_least`, asserted
  against a constant the way `naming.MINIMUM_SCANNED` already is. The pair it
  guards — `unformatted_files == 0` over a denominator that cannot be zero —
  is unchanged.
- **The sensitivity check widens beyond archiving.** T100 asks whether a
  committed key survives moving a task file; nothing asks whether one survives
  *adding* one. Every evidence key is compared across both mutations, and any
  key that moves under either is named. Otherwise the third instance of this
  gets found the same way the second did, by a PR going red for no reason.
