## What this is

Specification v2 settled what the tool does. It deliberately did not settle what
gets built in what order — `status/spec-v2-process.md` §2 says the steps are
"deliberately not aligned with the delivery phases in `status/plan.md`, which
are about build order", and that build order did not exist for v2.

This task produces it: `status/plan.md` rewritten against specification v2, with
`status/plan-v1.md` kept as the record of what v1 planned. Six layers rather
than four — RUNTIME and DOCUMENT are new, because a process specification needs
a process engine and because generated documents rebuild under different rules
from a derived profile. One task table covering both generations of work, a
measurable gate on every row, four milestones, and a named owner for each of the
thirteen step gates.

It also does what the brief's §6.3 asked the specification round to do and the
round did not: **reconcile the queue** — refine the tasks whose scope changed,
name what is superseded, and seed what nothing covered.

## The rule that matters

**A plan and a queue that disagree are worse than either alone.** The reason
this task exists is that they drifted: tasks were seeded from review findings,
the plan never learned about them, and the overlap sat unresolved until someone
read both documents side by side. `plan_queue_task_drift` counts the
disagreement in both directions, so the next drift is caught by a check rather
than by a reader.

**Three dimensions, because membership alone is not agreement.** Review found
both of the others in the first draft of this very task:

- **membership** — a task with no row, or a row with no task;
- **gate** — a plan row whose Gate cell contradicts the `gate` block in the
  task's payload. `gate_run.sh` executes the payload; a human reads the plan.
  Eight rows disagreed;
- **dependency** — a plan row whose `Depends` contradicts the queue's blocking
  `deps`. `queue_batch.sh` dispatches from the queue alone, so a prerequisite
  recorded only in the plan does not exist: S7 could have been dispatched
  before T34 and T35, the two tasks the plan sequences it behind.

The gate is a **count**, never a restatement of either side's length. Labels are
counted with multiplicity, so a duplicated row is reported rather than absorbed.

## Tests

`test_task_in_the_queue_without_a_plan_row_is_drift` in `tests/test_plan_v2.py`;
`test_plan_row_without_a_queue_task_is_drift`;
`test_a_payload_gate_differing_from_the_plan_is_drift`;
`test_a_plan_dependency_missing_from_the_queue_is_drift`;
`test_duplicate_labels_are_reported_not_collapsed`;
`test_evidence_log_is_not_read_as_a_task_table` — it carries a T# column and a
Gate column, and reading it as one would let a measured task pass without ever
being sequenced; `test_a_following_table_does_not_inherit_the_gate_column` — so
that safety is not a matter of where the blank lines fall;
`test_a_queue_line_that_is_not_an_object_is_reported_not_raised`;
`test_a_missing_plan_records_minus_one_not_zero` — a run that could not measure
must not look like a run that measured zero.
