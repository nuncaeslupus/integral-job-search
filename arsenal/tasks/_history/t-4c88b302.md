Imported from issue #310

Found while capturing the four probes for #260. Not about those connectors — it is about the adjudication rule every connector in this repository is admitted under.

## The rule

`connectors/ruled-out.yaml` requires that the repo's own matcher **and** a second, independent parser agree before a path is fetched, plus a negative control so that a `True` is distinguishable from a matcher that says yes to everything. The second parser is stdlib `urllib.robotparser`.

## The defect

**CPython's `robotparser` returns the *first* matching rule in file order, not RFC 9309 §2.2.2's longest match.** `Entry.allowance` iterates the rule list and returns on the first `applies_to` hit.

So on any robots.txt that opens with `Allow: /`, it answers `True` for **every** path in the file — including every path a later, longer `Disallow` covers. Measured on two live boards:

| host | target | repo matcher | stdlib | control | repo | stdlib |
|---|---|---|---|---|---|---|
| himalayas.app | `/jobs/api?limit=20` | True | True | `/apply`, `/jobs?page=2` | **False** | **True** |
| nofluffjobs.com | `/Python?page=1` | True | True | `/api/posting/123`, `/posting/abc` | **False** | **True** |

Both files open with `Allow: /`. `robotparser` never returned False on either one.

## Why it matters

The error is **fail-open**, and it is fail-open in the exact component that exists as the independent check. Two matchers agreeing means something only when both can disagree; here the second one cannot say no at all, so the rule silently becomes "the repo matcher decided" while the file records a two-parser adjudication. Every board admitted over a permissively-opening robots.txt was adjudicated that way.

Nothing was fetched that should not have been — the repo matcher is strictly stricter and it carried the verdicts. The hole is in the evidence, not (yet) in the behaviour.

## Related, and part of the same gap

`www.workingnomads.com`'s entire robots.txt is `User-agent: *` / bare `Disallow:`. No path on that host is disallowed, so **no negative control can exist**. The rule has no answer for that case today, and the honest thing — saying so — is currently indistinguishable from forgetting to do it.

## Scope

- Make the second parser's **competence** part of the adjudication, not assumed: before trusting an agreement, show the second parser returning False for at least one path on that same file. Where it cannot, the adjudication is single-parser and must be recorded as such rather than counted as agreement.
- Or replace the stdlib as the second reader with one that implements longest-match, and keep the competence check anyway — this failure was invisible precisely because nobody asked the second reader to prove it could refuse.
- Give "no negative control is possible on this file" its own recorded verdict, distinct from "no control was run".

## Gate

`robots_adjudications_without_a_competent_second_reader == 0`, denominated by every adjudication in `ruled-out.yaml` and every shipped connector package, with a floor so a scan that finds none reports `unmeasured`.

*(As filed. The acceptance gate below carries `robots_adjudications_misrepresenting_their_standing == 0` instead, and says why: under the literal name the honest answer is **19**, not 0, and it is committed as such rather than hidden behind a metric that counts something else.)*

## Acceptance gate

```gate
robots_adjudications_misrepresenting_their_standing == 0
evidence: status/evidence/T116.json
key: robots_adjudications_misrepresenting_their_standing
status-key: gate_status
```

The metric started as **`status/plan.md`'s own** —
`robots_adjudications_without_a_competent_second_reader`, declared in T116's plan
row before this implementation existed, which is what keeps the number from being
one the implementer chose to suit the code. The `requires: [human:gate]` line the
import left in the front matter is gone, and this fence replaces the
`arsenal:gate-placeholder` recipe: a prose gate runs nothing, and a gate that
runs nothing passes everything.

**A task editing its own acceptance gate is the one thing a task must not do
quietly, so what changed and why — twice, because it was edited twice.**

*First edit:* the metric name, the operator and the threshold were the plan's,
unchanged. What was added was where the number is read from — an evidence file
and a key — plus `status-key`, so a scan too small to mean anything reports
`unmeasured` instead of a zero.

*Second edit, the rename above:* the **second-reader audit of #328 found the name
was not describing what it counted, in the fail-open direction.**
`robots_adjudications_without_a_competent_second_reader` read **0** while **19 of
the 20 rows have no competent second reader** — the implementation had given that
name to the *structural* count of records that misstate their standing. The
defence offered was that the literal reading is outside this task's Scope; Scope's
second bullet says otherwise ("or replace the stdlib as the second reader with one
that implements longest-match, and keep the competence check anyway"), so the
literal metric is reachable in principle and a `0` under that name teaches the
next session the opposite of the truth. That is T108's `status_is_asserted` and
`#323`'s `incidental_duplicate_drops` a third time.

So the name keeps its meaning and loses the gate. It is committed in
`status/evidence/T116.json` under its own key at the honest **19**; the gate is
`robots_adjudications_misrepresenting_their_standing`, **0**, which counts records
claiming more than the file under them supports and is the property this module
can actually enforce. What would make the 19 fall is a second reader implementing
§2.2.2's longest match, seeded as **T120** (`arsenal/tasks/t-9d41c7f5.md`).

The zero is not the whole check, because a zero is also what an empty scan
reports. `integral.connector_policy --second-readers` **returns 1** on any of
these, none of which a do-nothing implementation would trip:

- a recorded `two_parsers_agreed` naming no path the second reader refused on
  the same file — the defect above, and the fail-open direction;
- a shipped connector package with no adjudication record at all, which is a
  fetch admitted with no second reader whatsoever;
- any of nine malformed control rows coming back clean, each a way the record
  could look complete while establishing nothing;
- any `COMPETENCE_FIXTURES` case classified against the RFC 9309 section it was
  derived from.

and **returns 3** — `unmeasured`, not a pass — when the scan falls under
`ADJUDICATIONS_AT_LEAST` or fewer than `PACKAGES_AT_LEAST` packages were found.
The denominators are committed as those floors and never as the count of the
day, so adding a connector is not an evidence drift (T100's finding, one module
over).
