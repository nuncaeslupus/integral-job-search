Imported from issue #727

`make test` already runs `pytest -n auto`. `make evidence`, by contrast, loops over `repo_gate --list-evidence-modules`, which lists 118 modules, and runs `uv run python -m integral.<m>` for each one in turn. Every module pays for interpreter and `uv` startup and waits for the previous one to finish. This is the "spawn-bound" shape that `claude-arsenal/references/performance-tuning.md` § "When parallelism is not the lever" describes.

`verified_gate.sh` runs `make host-gate`. On 2026-10-04 it took 13–37 minutes on a 4-core box at load ~15, while several sessions were gating at the same time.

Proposal:
- Run the evidence modules concurrently, for example with `xargs -P` or a small Python driver. Keep the per-module status line and the fail-on-drift behaviour.
- Measure the wall-clock before and after on an idle machine, and commit the numbers.
- Before parallelising, check that no two modules write the same evidence file or depend on another module's output. If any do, that ordering has to be kept.

## Notes

Shared-output check (dynamic, mtime snapshot around each of the 114 modules run serially): 162 files written, 161 by exactly one module. The only shared file is `status/evidence/T203.json`, written by `exclusion_live_round` and again by `sourcing_exclusions`, which runs the former as a subprocess; both write identical bytes and nothing reads it mid-run, so no ordering is needed. No module writes outside `status/evidence/`, and none reads another's output.

Measurement (`make evidence`, once each, idle machine, UV_PYTHON=3.12, `nproc` = 4, load average ~0.7 at start, no other gate running): serial loop on origin/main 179 s; `evidence_runner` with 4 jobs 50 s, 114 ok, no drift. Single runs, not a benchmark; the speed-up (about 3.6x on 4 cores) will be smaller on a loaded box.
