# Payload: t-00258c82 — one test file is the suite's serial floor

**Gate**: within one pytest session the live `src/` tree is analysed once, and a
cached analysis is still an analysis — it must go red on a tree that a fresh one
would go red on.

## Tests

- `test_the_live_tree_is_analysed_once_in_a_session` in `tests/test_floor_sweep.py`
  — counts full analyses of the live `src/` tree across a session, instrumented at
  the analysis entry point, **not** by counting call sites in the test file. A count
  derived from the file it is about is a bound derived from the thing it bounds.
- `test_a_cached_analysis_still_sees_a_changed_tree` in `tests/test_floor_sweep.py`
  — the negative control, and the fail-open direction. Analyse, write a floor that
  breaches its population into the tree, analyse again: the second result must
  differ. A cache that answers from its first call regardless is nine tests passing
  over a measurement nobody took.
- `test_every_live_tree_caller_reaches_the_cache` in `tests/test_floor_sweep.py`
  — derived over the module's no-argument entry points (`measure`, `_main`,
  `write_evidence`, `write_prose_clearance_evidence`, the marker-restatement
  clearance), so an entry point added later is covered without anyone remembering
  to. Enumerating today's five buys one more finding; deriving the axis ends it.

## References

- `tests/test_floor_sweep.py` — 119 tests, **394.4s**, 32.8% of the suite's total
  CPU. The suite's wall clock is **413s**. `--dist loadfile` cannot split a file
  across xdist workers, so this one file *is* the floor under every run; the other
  807 CPU-seconds finish across 11 workers in about 70s and those workers then idle
  for five minutes.
- `src/integral/floor_sweep.py` — `measure()` with no argument analyses the live
  tree. Measured on 2026-09-21: **13.2s** per call, 85 floors, and the cost is
  O(floors × modules) rather than waste. `_module_infos()` (glob + `ast.parse` over
  `src/*.py`) is the obvious cache and is **not** where the time goes; the analysis
  is.
- `_main()` is why the three worst tests cost what they do: it calls
  `write_evidence()`, then `write_prose_clearance_evidence()`, then the
  marker-restatement clearance — three full analyses of the same tree per call.
  Ten no-argument entry points in the test file, ~20 analyses, ~13s each.

## Context

Found while answering "can the tests run faster". They already run in parallel —
12 workers — and that is exactly why this is visible: parallelism moved every other
file out of the way and left one file standing alone for 394 seconds.

**Caching is the fix, not splitting.** Splitting the file so `loadfile` can spread
it would take the suite to ~130–150s without changing a test, but it buys nothing
the cache does not and it spends the cost three ways instead of once. It is also
the riskier edit: `--dist loadfile` exists because `tests/test_repo_gate.py` writes
into the live working tree, and spreading a file across workers is only safe for a
file that does not. `floor_sweep.py` was checked and writes nothing — it is a pure
AST reader, and every constructed-tree test uses `tmp_path` — so splitting is
*available*, and it is still the second-best answer. Mention it in the PR if the
cache lands short of the gate; do not do both.

The fail-open direction is the whole risk here and it is this repository's own
recurring family. A cache keyed on anything weaker than the tree's contents — a
path, a session id, a bare `lru_cache` on a no-argument function — makes nine
tests green over one stale result, and the suite then certifies a tree it never
read. That is a check pinned against a proxy for the property rather than against
the property. The negative control above is not optional decoration; it is the
only thing separating this task from the defect it is trying to avoid.
