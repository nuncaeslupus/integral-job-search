Imported from issue #552

`matches_aim` is used to **order** results and never to exclude them, so every advert a board returned for any query is presented. On a live round, 108 of 124 offers shown to a candidate matched none of their six search terms in the title.

What the candidate found in the first screen, unprompted:

```
Offensive Security Engineer
Administrativo/a Comercial Francés e Inglés
Aerial Robotics Research Engineer
Quality Assurance Rater - Spanish ES
Senior Software Engineer - Mobile
```

Their aim is `prompt engineer`, `applied ai engineer`, `agentic engineer`, `LLM engineer`, `generative ai engineer`, `ai evals`. None of those five is a near miss; they are different jobs. Their verdict: *"esta criba no ha funcionado nada bien"*.

Two separate causes, and the second is the one worth fixing carefully:

- **Nothing rejects.** A low-relevance offer sorts last and is still shown. "Sorted last" and "not shown" are the same thing for the top of a list and opposite things for a list of 124.
- **`matches_aim` is title-and-body whole-word matching**, so a body that mentions LLMs once makes an administrative vacancy match. Relevance has to be a score over the role, not a substring test over the advert.

The fix must not become a keyword blocklist — the enumeration failure in #547 is the precedent, and a list of job titles has no last element.

## Acceptance gate

```bash
uv run python -m integral.relevance
```

`offers_presented_below_the_relevance_floor == 0`, with the floor fixed in the candidate's own profile rather than in code, **and** `on_aim_offers_rejected == 0` over a fixture set of adverts that match the aim in wording the terms do not contain literally (`LLMOps`, `RAG engineer`, `ingeniero de IA generativa`). The second number is the fail-open direction reversed: a filter measured only by what it removes reaches zero by removing everything.

Filed from a live candidate round, 2026-09-22.
