# D-24: A retracted episode stays sendable — approval outlives its evidence


```bash
uv run --extra dev pytest tests/test_approval.py -k retraction -q
uv run --extra dev python -m integral.approval
```

`src/integral/approval.py` must write `status/evidence/D-24.json`. It already

than into it, so both gates keep reading their own file.

## Why

Retracting an episode does not stop it being sent. Approve an episode for
`<offer>/v1`, retract its evidence row, then send `v1` — `record_sent`
re-measures, finds the line backed, and records the send.

`measure_prepared` backs an episode line by `approvals.json` and nothing else:

```python
if claim.section == "episodes":
    if claim.text in approved:      # approvals.json; the evidence log is never consulted
        backed[(claim.document, claim.text)] += 1
    continue
```

Retraction never touches `approvals.json`. `approval.py` contains no mention of
retraction; `retraction.py` contains no mention of approval. The approval
outlives the evidence it was given over, and the only check at the send boundary
consults the approval.

`record_sent` does re-measure — its docstring is explicit that *"a file can
change between drafting and sending"* — but re-measuring against an unchanged
approvals file cannot notice the underlying row is gone.

**This is the divergence**: process spec §6.2 says an episode reaches an
employer-bound document *only with per-use approval*, and retraction is how a
candidate withdraws the thing that approval was given over. The code keeps the
approval and loses the withdrawal. **Fail-open** — the check said yes to exactly
what it exists to refuse.

## What it must not become

**Do not reinstate a store lookup for episode backing.** That rule is deliberate.
An approval names `(offer_id, version, text)` — *"the text, never a list
position"* — because *"a store index is a fact about the order of a list the
candidate edits; inserting an unrelated episode above an approved one used to
invalidate the approval, and editing one used to leave the old approval sitting
there."* Routing authority back through the store reintroduces exactly that.

The fix belongs on the other side: when a retraction lands, invalidate or require
re-confirmation of any approval naming that episode's text. Which of the two is a
design call — invalidation is safer, re-confirmation is kinder to someone
mid-application. Settle it in the task, do not leave it to the implementation.

**A zero count over an empty input set is not a pass.** Record
`retracted_episodes_evaluated` — approvals actually checked against retracted
rows — and write `gate_status: "unmeasured"` whenever it is `0`, `"measured"`
otherwise. A run that examined no retraction must not report a clean gate.

## Tests — write these RED first

`test_a_retracted_episode_cannot_be_sent` in `tests/test_approval.py` — approve
an episode for a version, retract its evidence row, assert `record_sent` raises.
**This must fail before any fix.**

`test_an_unretracted_approval_still_sends` — the fix must not turn every send
into a refusal.

`test_retraction_after_send_does_not_rewrite_the_record` — an application record
is immutable once written.

`test_the_gate_does_not_pass_on_an_empty_input_set` — assert
`retracted_episodes_evaluated` is written and non-zero.

Per `CLAUDE.md`, the fixtures for this gate should be written by a session other
than the implementer: it compares two representations of the same sentence, and
it is fail-open — both triggers for that rule.
