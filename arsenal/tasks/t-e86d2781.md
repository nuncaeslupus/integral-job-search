Imported from issue #560

Found while measuring #558: `Offer.model_validate_json` raises on 68 of one candidate's 1,314 stored offers, so every reader that loads the store has to skip rows or crash.

```
salary.period
  Input should be 'year', 'month', 'week', 'day' or 'hour' [input_value='HOUR']
```

## Measured

One candidate's store, 2026-09-23 — every `salary.period` value present:

| value | rows | canonical? |
|---|---|---|
| `annual` | 30 | no |
| `hourly` | 15 | no |
| `year` | 12 | yes |
| `MONTH` | 11 | no |
| `HOUR` | 4 | no |
| `YEAR` | 4 | no |
| `monthly` | 4 | no |

**68 rows non-canonical, 12 canonical.** So the backfill normalised the minority.

## Why it matters beyond the exception

Commit f806c8e5 ("backfill offers written before T170 with a raw `salary.period`", #538) is the fix that was supposed to close this. It did not reach these rows, and nothing caught that, because **the backfill's own evidence never re-reads the store it wrote**. A migration whose gate does not load every row afterwards can report success over rows it skipped — the same shape as a check pinned against a proxy rather than against the property.

Two spellings are case variants (`HOUR`, `YEAR`, `MONTH`) and three are different words (`annual`, `hourly`, `monthly`). A case-fold alone fixes 19 of the 68.

## Acceptance gate

```
stored_offers_that_fail_offer_validation == 0
```

Measured by **loading every offer file in a store through `Offer.model_validate_json`**, not by counting what the migration touched. The denominator must be the store, or the gate is the migration grading its own homework.
