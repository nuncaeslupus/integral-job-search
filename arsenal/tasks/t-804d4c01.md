# T70: Robots matching that cannot fail open

## Acceptance gate

```gate

```

```bash
uv run --extra dev pytest tests/test_robots.py -q

```

The `bash` block regenerates `status/evidence/T70.json`; the `gate` block asserts the
number in it.

## Why

`src/integral/robots.py:24` delegates matching to `urllib.robotparser`. Measured on 2026-08-25, it is wrong in both directions:

```
longest-match:   /jobs/public/x -> False   (RFC 9309 says True)   fails closed
blank-in-record: ClaudeBot /x   -> True    (site said Disallow: /)  fails OPEN
```

The second is the dangerous one. `connectors/trabajos_es/connector.yaml`'s header records that **tecnoempleo.com** and **remoteok.com** were ruled out because their `robots.txt` names `ClaudeBot` with `Disallow: /`. If either file carries a blank line inside that record, our checker currently reports *allowed* — and every `meta.yaml` asserting `robots_txt: respected` is then a false statement shipping to contributors.

## What it must not become

**Do not fix this by post-processing `RobotFileParser`'s answer.** The record grouping is what is wrong, so the parse has already lost the information by the time it returns. Write the matcher. It is ~40 lines: group by `User-agent` (blank lines are whitespace, not terminators), select the most specific matching group, then longest-match with Allow winning ties.

**Failing closed is acceptable where genuinely ambiguous; failing open never is.**

## Tests — write these RED first

`test_a_blank_line_inside_a_record_does_not_end_it` in `tests/test_robots.py` — a `Disallow: /` following a blank line still binds its agent group.

`test_longest_match_wins_over_file_order` — an `Allow: /jobs/public/` beats an earlier `Disallow: /jobs/`, per RFC 9309 §2.2.2.

`test_allow_beats_disallow_on_an_equal_length_tie` — the tie-break direction is Allow.

All three must fail before the fix.
