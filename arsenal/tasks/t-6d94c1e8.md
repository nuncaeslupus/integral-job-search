## Where this comes from

`tools/profile_guard.sh` is a PreToolUse hook refusing any `profiles/` access
outside the identified handle. Correct, and it works. But the active handle is
**session-bound**, and in one session working on a single application it was
lost **five times** — each loss surfacing as `no candidate is identified yet;
§6.1` on an edit to a file the session had been editing for an hour.

The recovery is `write_active_handle(default_profiles_root(), '<handle>',
session_id=...)`. Two things make it more expensive than it looks:

- **The guard inspects the whole Bash command string before it runs**, so
  `restore && edit` in one call is refused as a unit. The restore has to be its
  own call. A session that does not know this tries the compound form first.
- Nothing tells the session the handle is gone until a write fails, so the loss
  is always discovered by an interruption.

## What to change

Either make the handle survive what is currently losing it, or — if the
session-binding is deliberate — make the refusal **self-healing**: the guard
already knows the handle it would need, so it can name the exact restore command
in its refusal message instead of a section reference.

Diagnose before choosing. `§6.1` is the current message and it points at a
document, not at a command; at minimum that message should carry the one line
that fixes it.

## Tests

`test_refusal_names_the_restore_command` — the refusal text contains a runnable
command, not only a spec reference.

`test_compound_command_refusal_is_explained` — a command that restores and then
writes is still refused, and says why in one line.
