Batched non-blocking findings from the PR #914 second-reader rounds on t-07b591f4
(the profile_kit module). None is a trust-boundary or common-case bug, so they were
filed rather than fixed in that PR (owner policy C: round-two non-security findings
are filed, policy G: batched into one task).

1. **Multi-line description bleeds out of the markdown bullet.** `_texts_md` renders
   each field as `- **{label}:** {value}`. A `description` with embedded newlines (a
   multi-paragraph job description from the store) puts lines 2+ outside the bullet, so
   they no longer read as part of that field when the texts.md is pasted into a profile
   site. Indent continuation lines, or render the value as a block.

2. **Source-suffix lookup is case-sensitive.** `_place_logo` matches `<slug><ext>` for
   ext in `_RASTER` (all lowercase). A file dropped as `<slug>.PNG` / `<slug>.JPG` is
   reported `missing` though a logo is present. Match the suffix case-insensitively.

3. **`_unique_slug` can still collide with a natural slug (fail-open overwrite).** The
   generated suffix `<base>-2` can equal the real slug of another entity, so one
   `texts.md` overwrites another's. E.g. organisations `東京大学`, `北京大学`, `Entity 2`
   → slugs `entity`, `entity-2`, `entity-2`; likewise `C&A`, `C.A.`, `C-A 2` →
   `c-a`, `c-a-2`, `c-a-2`. Fix: track the set of slugs already emitted and bump `n`
   until the candidate is free, not just the per-base count.

4. **White-trim tolerance is measured on luma, not per channel as its comment says
   (fail-open crop).** `square_logo` does `ImageChops.difference(...).convert("L")`
   then `> _WHITE_TOL`. Luma weights blue 0.114 / red 0.299, so a pale-channel part of
   a mark (e.g. `(255,255,140)`, 115 off on blue) scores below 16 and is cropped off —
   contradicting both the 16/channel comment and the spec's "keep marks such as TM".
   Fix: threshold the per-channel maximum (e.g. `ImageChops.lighter` over
   `diff.split()`), not `convert("L")`.

Gate: add fixtures to tests/test_profile_kit.py pinning all four — a multi-line
description whose continuation lines stay within the field; an uppercase-suffix source
that is squared rather than reported missing; the two collision triples above asserting
three distinct slugs; and a white source with a `(255,255,140)` block beside a dark
block, asserting the pale block is inside the trimmed bbox.
