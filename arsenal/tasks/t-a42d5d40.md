```
ConnectorError: locale: Input should be 'en', 'es' or 'ca'
```

## What widening it actually costs

The owner's standing rule is that supported languages behave identically — a half-added language is a silent feature, not a partial one. Measured tonight:

| | per new language |
|---|---|
| dimension files carrying language-tagged cues | **41** |
| cue entries today | en 31, es 38, ca 31 |
| candidate-facing strings in `strings/catalogue.json` | **24** |
| corpus adverts | ca 90, es 93, en 25 — **pt/de/fr/it/nl: 0** |

The corpus row is the binding one. `T3.language_slices_with_no_corpus_hit` is 10 today; adding a language with no adverts in it would add up to 41 more — one per dimension — and that gate would be reporting the truth.

So adding a language is: a cue vocabulary across 41 dimensions, a strings pack, **and a corpus in that language**. It is not a connector-sized task, and it is upstream of every connector-sized task for those five countries.

## What this means for the backlog

`wanted.yaml` should say so at the top, and its ranking basis — "country has zero connectors" — is measuring the wrong thing while this holds. The honest ordering is: **language first, then boards in that language.**

It also reframes #355 and #356. Both gaps are real and #355 is now closed, but neither was ever the binding constraint for those countries. Worth knowing before someone spends a day closing #356 expecting a German connector at the end of it.

## Suggested shape

One language at a time, end to end, with the corpus drawn by specification through the connectors that already exist for that language — which for a new language is none, so the ordering has a bootstrap problem worth naming before starting. Portuguese is the cheapest first candidate only because `net-empregos.com` is already surveyed, robots-cleared, decoded and field-mapped (`connectors/ruled-out.yaml`, `engine_gap_charset`); the moment `pt` is a language, that package is a short PR.
