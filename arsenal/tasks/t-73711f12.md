Four notes, one behaviour. The candidate asked to be **directed**:

> It is good that you give options to the user, but you should direct it more.
> If you consider that having more info is better, you must enforce it. […] You
> know what is needed, not the user, so saying it is better than letting the
> user decide. You must justify your decisions and recommendations.

And to be **drawn out**:

> You should tell the user at the beginning and some other times that this is a
> conversation […] "any anecdote, good or bad experience can be very helpful;
> things that you do at your spare time, how you are, etc. can give very useful
> insights". You must induce the user to talk as much as possible.

And to be **followed up on**: *"Anything that intrigued you about the CV or our
conversation, you must pull the string."* The concrete miss was a developer
never asked about their public repositories — which generalises: every field
produces artefacts that speak louder than a CV line, and the intake should ask
for **the ones this candidate's field produces**, not a hardcoded GitHub prompt.

There is an existing shape to respect. `T36` deliberately makes re-entry an
**offer, not an action**, and `T34`'s runtime answers *which steps may run*. This
task must not turn consent into coercion. The distinction it draws: **the choice
stays the candidate's, the recommendation becomes ours**. An offer with no
recommendation attached is the defect; an offer the candidate declines is not.

Small rider from the same thread: when the context is growing, say so and offer
to compact. That is the same behaviour — the tool knowing something about the
session that the candidate cannot see, and saying it.
