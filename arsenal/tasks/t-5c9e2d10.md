# D-25: The simulation prompt's parity table is argued, never measured

## The run this was waiting for has happened

`requires: [surface:human]` held this task because no bot can hold the candidate
side. **A human did, on 2026-08-29/30** — the owner ran a full session as the
candidate, in Spanish, with the meta-channel carried in `[[...]]` markers.

The observations are in the `test-mode` note ledger, which lives outside the
repository by design: the skill forbids writing a note anywhere under a
candidate's tree, so the ledger is reachable only from the owner's laptop, via
`query_notes.py --id <session>`. 27 notes, each tagged with the step it was made
at, covering identify, intake, constraints, history, reactions, preferences,
sourcing and ranking. That is **8 of the 13 stages observed**, with provenance,
which is what `test_an_observation_without_transcript_provenance_is_rejected`
asks for. Traits, understanding, feedback, application and interview_log were
never reached and stay unverified; the metric must count them rather than
quietly dropping them.

**Several observations contradict the desk verdict, which is the interesting
part** — `test_a_verdict_changed_by_an_observation_is_recorded_not_overwritten`
exists for exactly this and now has subjects:

| stage | §2 says | the run showed |
|---|---|---|
| 1 intake | faithful | the CV could not be read, and the session continued anyway (T97) |
| 6 preferences | degraded | worse — the elicitation item had no coherent answer (T96) |
| 7 sourcing | manual | the loop never ran: no connector was proposed, let alone built (T91) |
| 9 ranking | faithful | three adverts and a stop, presented as an exhausted market (T91, T92) |

A verdict of *faithful* derived by reading the skill, contradicted by the one run
anybody has done, is the whole argument for this task. Record both; do not
overwrite §2 in place.

Extracting the observations is a laptop step, and the notes must be quoted into
the record **without** the candidate's identity, history or any path under the
profile store — the same boundary that keeps the ledger out of this repository.

**That sentence is not the guard.** Written as prose it is a promise the gate
cannot check, and every listed test passes over an evidence file carrying a
candidate's name: they assert that provenance is present, not that identity is
absent. `status/evidence/D-25.json` is committed and public, so the failure is
one-way and permanent. The refusal has to run before anything is persisted, and
it belongs in the gate:

- `test_an_excerpt_carrying_a_profile_store_path_is_refused`
- `test_an_excerpt_carrying_the_candidate_handle_is_refused`
- `test_the_refusal_runs_before_the_evidence_file_is_written` — a check that
  fires after the write has already published the thing it objects to.

## Why

`docs/simulation-prompt.md` §2 classifies all thirteen stages — eight faithful,
four degraded, one manual — and the file says plainly that **nobody has run §3 in
an actual chat**. Every verdict in that table was derived by reading the step
skills and reasoning about what prose can carry. None was observed.

That is this repository's own named failure: a claim about behaviour, published,
with no measurement behind it. It shipped anyway because the alternative was
withholding a usable artifact indefinitely, and because the file states the gap
rather than hiding it — the D-12 and D-23 precedent, where the mechanism ships
and the accuracy waits.

**The reasoning that produced the table has a known error rate.** The PR that
introduced it (#252) took twenty-two review findings over six rounds. Two were
mechanisms asserted without reading the function they described; one was a
privacy guarantee that was true of the tool and false of a chat. A table built
the same way, by the same means, is not evidence about a conversation nobody has
had.

## Precondition — this cannot start early

**The real tool must have been run the actual way first**: a genuine session
through Claude Code, a real candidate, far enough to exercise the stages being
compared. Comparing the simulation against a second act of reasoning about the
tool measures nothing; the whole point is to compare it against the tool's
observed behaviour.

No task tracks that first real run, so this one cannot declare a `deps` edge to
it. `requires: [surface:human]` keeps autonomous selection off it —
`task_select.py` is invoked without `surface:human` by the worker loops — but a
person picking this up should confirm the precondition holds before starting,
because nothing mechanical will.

The `test-mode` skill (S11) is the intended instrument for the real run: it
captures notes about the tool during a live session without disturbing it, which
is exactly the record this task needs.

## What to do

1. Run the real tool far enough to observe each stage's actual behaviour, using
   `test-mode` to capture notes as it goes.
2. Run `docs/simulation-prompt.md` §3 in a plain Claude conversation, as a
   candidate would, with the same inputs where that is possible.
3. For each of the thirteen stages, record an observation: what the tool did,
   what the simulation did, and whether the §2 verdict (`faithful` / `degraded` /
   `manual`) survives contact.
4. Correct §2 where it does not. A verdict that moves is the finding, not a
   failure of the task.
5. Correct §3 where the run shows the prompt misbehaving — a stage it skips, a
   cap it ignores, a rule it breaks.

## What it must not become

**Do not verify a stage by reasoning about it.** That is what produced the table.
An observation is something that happened in a transcript, and the evidence
record must name it.

**Do not quietly downgrade the table to make it pass.** Marking everything
`degraded` would zero the metric and measure nothing. The gate counts stages
whose verdict no observation backs, so an unobserved stage is unverified whatever
its verdict says.

**A zero count over an empty input set is not a pass.** Record
`simulation_stages_evaluated` — stages actually observed — and write
`gate_status: "unmeasured"` whenever it is `0`, `"measured"` otherwise. Thirteen
stages evaluated is the denominator this task exists to raise from zero.

**And "cites an observation" must not be satisfiable by prose.** The first draft
of this task said the gate counts stages whose verdict no observation backs, and
left "observation" undefined — so a row reading `{"stage": 8, "observation":
"the model would have to do this by hand"}` would have counted. That is a
reasoning-only claim wearing the word, and admitting it would reproduce inside
this gate exactly the defect the task was filed about. Caught in review of the
PR that added the task.

So every observation carries **provenance**, and the gate rejects one that does
not:

```json
{
  "stage": 8,
  "verdict_claimed": "degraded",
  "verdict_observed": "degraded",
  "provenance": {
    "source": "tool",
    "session": "cse_…",
    "recorded_at": "2026-09-…",
    "excerpt": "…the transcript line that shows it…"
  }
}
```

- `source` ∈ `tool` | `simulation` — a stage needs one of each to be compared,
  so two rows per stage, and a stage with only one is unverified.
- `session` identifies the run. For the tool side it is the Claude Code session;
  for the simulation side, the conversation.
- `excerpt` is text that actually appeared. Empty, absent, or paraphrased fails.

`test_an_observation_without_transcript_provenance_is_rejected` is what makes
this executable rather than a request.

## Tests — write these RED first

`test_every_stage_verdict_cites_an_observation` in
`tests/test_simulation_parity.py`.

`test_a_stage_with_no_observation_counts_as_unverified`.

`test_an_observation_without_transcript_provenance_is_rejected` — an observation
missing `provenance`, or carrying an empty `excerpt`, does not count as backing
a verdict. This is the one that stops the gate being satisfied by prose.

`test_a_stage_observed_on_only_one_side_is_unverified` — a stage needs both a
`tool` and a `simulation` observation; one alone compares nothing.

`test_the_gate_reports_unmeasured_when_nothing_was_observed` — assert
`simulation_stages_evaluated == 0` yields `gate_status: "unmeasured"`.

`test_a_verdict_changed_by_an_observation_is_recorded_not_overwritten` — the
original verdict and the observed one are both retained, because the difference
between them is the measurement.
