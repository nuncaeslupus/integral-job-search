Imported from issue #351

Measured live 2026-09-05, immediately after T126 (#350) made sourcing work at all:

```text
82 offer(s) added from 6 board(s)
  DROPPED getmanfred_es: 22 of 22 row(s) were not offers — connector produced no 'text' field
  DROPPED trabajos_es:   28 of 40 row(s) were not offers — connector produced no 'text' field
```

`sourcing.source()` builds and fetches **list** requests only. For a board whose list page carries a teaser rather than the ad body — or, in `getmanfred_es`'s case, an API index with no body at all — `build_offer` gets no `text`, `Offer` refuses a blank one (rightly: there is nothing for extraction to find evidence spans in), and every row is dropped.

Result: `getmanfred_es` contributes **0 of 22**, `trabajos_es` **12 of 40**. Both are shipped, usable, correctly-parsing connectors. The schema already has what is needed — `detail_url_template`, `parse_detail_page`, and `build_offer(detail_fields=...)` — and none of it is reached.

## Why it was left out rather than bolted on

Fetching each card's detail page multiplies requests by the page size: one list page of 30 cards becomes 31 requests. That needs the thing `robots.delay()` exists for and which the current driver never calls, because with one request per board it had nothing to pace. Specifically:

1. **Crawl-delay honoured between detail fetches**, per host, from `robots.delay(url, floor)` — not a global sleep.
2. **A per-item failure must not lose the item.** A detail fetch that 404s or times out should still yield the offer if the *list* row carried enough to build one; today it would be all-or-nothing.
3. **A budget.** Six boards x 30 cards is 180 requests for one sourcing pass. Whether that is per-run, per-board, or per-host is a decision, not a default.
4. **Re-fetch avoidance.** An offer already in the tree does not need its detail page read again; `collect_offer`'s tombstone and id matching already knows this, but only *after* the fetch, which is the wrong order once the fetch is expensive.

None of that is hard. All of it is a different shape from "issue one request per board", which is why it is here rather than in #350.

## Gate

Not "detail pages are fetched" — a fixture satisfies that. The honest metric is that **a board whose body lives on the detail page stops losing rows**: `rows_dropped_for_a_missing_body == 0` over a run against the committed captures, with the denominator being rows parsed, floored so a run that parsed nothing cannot pass. `getmanfred_es` at 22-of-22 dropped is the control: it must go to 0, and if the metric reports 0 while getmanfred still yields nothing, the metric is measuring the wrong thing.

Depends on #350.
